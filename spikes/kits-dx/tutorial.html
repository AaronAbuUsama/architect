Building acme on Architect, start to finish

From an empty folder to a project with wallets, payments and email kits mounted. Each step says whether it works today on layer/3 or is proposed by the K1 decision (design/decisions/K1-kits.md).

Where code runsruns on the operation: server, or the client's own device.
Who may reach itallowed, narrowed by credential kind: session, key, device, agent. Enforced on every route.
What existsThe environment: which credential kinds it issues, what it deploys and publishes.
A kitA package laid out like a project, mounted by one file in blueprint/kits/.

6Journeys first today · flags and --unbuilt proposed

An author, a different agent from the builder, writes the journey and its starting world. Journeys live in blueprint/journeys/.

$ architect add journey "spend within an allowance" --starts funded --cast olga:grantee
export default Blueprint.journey("spend within an allowance", {
  cast: { olga: grantee }, starts: "funded",
  steps: (s) => [
    s.step("olga spends some", s.olga.run(spend, { allowance: s.world.allowance, amount: 120n, memo: "train" }),
      expect((a) => a.remaining).toBe(380n), emits(AllowanceSpent, { … }), machine.isIn(s.world.allowance, "active")),
    s.step("olga can't spend more than is left", s.olga.run(spend, { …, amount: 400n }),
      refuses(AllowanceExceeded, { remaining: 380n }), noEvents()),
  ],
});

Who may reach it

10Narrow by credential proposed

The principal records how it arrived: a browser session, an API key, the CLI's device login, or an agent's OAuth token. Better Auth already issues all four. With no via, every way in is allowed, so acme does not change.

allowed: [grantee]                                      // every way in
allowed: [Blueprint.signedIn.via("session", "device")]  // people at a browser or a terminal
allowed: [holder.notVia("agent")]                       // anyone holding it, except through an agent's token

The runtime refuses with NotAllowed on every route, so an agent's token on the HTTP API is refused too. Hiding a tool from MCP alone would not be security. An agent handed an API key arrives as key: to stop keys too, narrow to session and device.

SurfaceGets an operation when
serverit runs on the server
SDKit admits session or key; a client operation is local code
CLIit admits device or key; client operations run in the CLI process
MCPit admits agent and does not run on the client
docs, portalalways, marked with where it runs and who may reach it

import { Blueprint } from "@architect/blueprint";
import wallets from "@architect/kit-wallets";

export default Blueprint.use(wallets, {
  choices: { browserSigner: "passkey" },   // every choice the kit declares, at its default

The kit's things keep their names: wallet.create, wallet.link. A clash with an app thing fails check, naming both files; renaming the mount file prefixes the kit's things. A mount can narrow or omit the kit's operations, by reference, never widen them.

13Wallets on the device proposed

Making a key is client side, so wallet.create runs on the device. Linking signs the server's Sign-In with Ethereum challenge on the device, so wallet.link is a client operation over two server operations.

// kit-wallets/blueprint/things/wallet/verbs/link.ts
export default Blueprint.operation(Wallet, {
  description: "Link a key on this device to your account, by signing the server's challenge.",
  runs: "client",
  payload: { address: Address }, answer: { wallet: Wallet.fields.id },
  allowed: [Blueprint.signedIn.notVia("agent")],
  steps: {
    challenge: Blueprint.step.call(challenge),            // server
    sign: Blueprint.step.dependency(Signer.signMessage),  // here, on the device
    complete: Blueprint.step.call(complete),              // server: verify, consume, link
  },
});

14Payments and email proposed

Not every kit has operations. Email gives a dependency your handlers call, a delivery record, and an inbound entry for bounces. Payments gives checkout.start, a Stripe webhook, and a refund dependency acme wraps in its own operation, because a refund needs acme's own owner role.

$ architect add kit @architect/kit-payments
$ architect add kit @architect/kit-email
  ~ blueprint/environments/production.ts   + STRIPE_KEY, STRIPE_WEBHOOK_SECRET, RESEND_KEY (names only)
blueprint/things/invitation/verbs/send.ts
steps: { insert: Blueprint.step.database(), mail: Blueprint.step.dependency(Mail.send) },
src/invitation/send.ts
yield* steps.mail(mail.send({ to: email, subject: "You're invited to acme", text: `Accept: https://acme.dev/i/${invitation}` }));

In local and test worlds each kit uses a real local stand-in, never a mock: a local mail sink whose messages journeys can check, stripe-mock with webhooks signed by the world's own secret, test keys for wallets, Anvil for a chain.
