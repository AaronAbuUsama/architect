# Spike: mcp-oauth

Throwaway. Standalone package (own `pnpm-workspace.yaml`, own lockfile), modelled on `spikes/better-auth-workerd/`.
Never imported by packages. Feeds D3 #10 and #11 and build steps L2.07 and L2.08.

**Question.** On local workerd and D1, can `@better-auth/oauth-provider` 1.7.15 with the `jwt` plugin be the OAuth 2.1
server for a remote MCP server on `@modelcontextprotocol/sdk` 1.32.2 (stateless web-standard streamable HTTP), with an
MCP SDK client completing OAuth headless as a signed-in person and a person without the role refused?

**Answer.** Yes. One worker, one D1, no Durable Object and no KV. `scripts/run.ts` runs all six proofs plus five
extra checks (33 checks, all pass, exit 0) against a real `wrangler dev` 4.156.1 and real local D1, then stops
everything (`pgrep` finds nothing). Four things differ from what the design assumed (see Found 4, 5, 7, 8).

Layout:

- `src/auth-options.ts`: Better Auth options shared by the worker and the schema script: email and password, `bearer`,
  `jwt`, `oauthProvider`, `deviceAuthorization`, every model renamed `auth_*`.
- `src/auth.ts`: `makeAuth(env, origin)` per request on `env.DB`.
- `src/mcp.ts`: a fresh `McpServer` per request with `CfWorkerJsonSchemaValidator`, one tool `allowance.get`,
  `WebStandardStreamableHTTPServerTransport` (`sessionIdGenerator: undefined`, `enableJsonResponse: true`).
- `src/worker.ts`: routes: `/api/auth/*`, path-aware discovery, `/jwks`, `/.well-known/oauth-protected-resource`,
  `/login` and `/consent` (echo stubs), `/me`, `/mcp` (verify bearer with `jose` against the local JWKS: issuer and
  audience checked; 401 with `WWW-Authenticate: Bearer resource_metadata="..."` otherwise).
- `migrations/0001_auth.sql` (generated by `scripts/generate-schema.ts`, same DummyDriver trick as the sibling spike),
  `migrations/0002_roles.sql` (the app's own `roles(person_id, role)`).
- `scripts/flow.ts` (the proof as functions: SDK `Client` + `StreamableHTTPClientTransport` + a headless
  `OAuthClientProvider`), `scripts/run.ts` (orchestrates and asserts).

```bash
pnpm install
printf 'BETTER_AUTH_SECRET=%s\n' "$(openssl rand -hex 32)" > .dev.vars       # random local value, gitignored
node --experimental-strip-types scripts/generate-schema.ts                    # rewrites migrations/0001_auth.sql
node --experimental-strip-types scripts/run.ts                                # everything; exits 1 on any failed check
```

`run.ts` wipes `.persist`, applies the migrations, starts `wrangler dev --port 8802 --inspector-port 0 --persist-to
.persist`, signs up ada and bob, grants ada the `allowance-reader` role with operator SQL (`wrangler d1 execute`),
runs the checks, kills the process group and runs `pgrep -fl "[w]orkerd|[w]rangler"`.

## What was found

1. **Tables.** `getMigrations` with a DummyDriver emits 13 Better Auth tables, all `auth_`-prefixed by `modelName`
   (core: `user session account verification`; plugins pass `schema: { x: { modelName } }`): `auth_user`,
   `auth_session`, `auth_account`, `auth_verification`, `auth_jwks`, `auth_oauth_client`, `auth_oauth_resource`,
   `auth_oauth_client_resource`, `auth_oauth_refresh_token`, `auth_oauth_access_token`, `auth_oauth_consent`,
   `auth_oauth_client_assertion`, `auth_device_code`. Foreign keys follow the renamed tables. Applied by
   `wrangler d1 migrations apply --local` in 1.5 to 2.2 s. Plus the app's `roles`. Sign-up 126 to 168 ms (scrypt),
   sign-in about 68 ms, wrong password 401. Check 1a to 1e.
2. **JWT signing works on workerd.** `/jwks` (and `/api/auth/jwks`) serve an Ed25519 (`EdDSA`) public key; the first
   call generates and stores the key in `auth_jwks` (about 15 ms), private key encrypted at rest. Check 2a, 2b.
3. **The token for `resource=<mcp url>` is a JWT that verifies.** Header `typ: at+jwt`, `alg: EdDSA`, `kid` from
   `/jwks`; claims `sub` (the person id, `per_...`), `iss` = `http://localhost:8802/api/auth`, `aud` = `[mcp url,
   <issuer>/oauth2/userinfo]` (an array, because `openid` is in the scope; verify with a membership check, which
   `jose` does), `client_id`, `scope`, `sid`, `jti`, `exp` 1 h. The refresh token (`offline_access`) yields a new
   verifying JWT for the resource. Check 2c, x3.
4. **A resource must be declared.** `resources: [MCP_URL]` plus `clientRegistrationDefaultResources: [MCP_URL]` makes the
   token a JWT with that audience. A `resource` the server does not list is refused: the authorize redirect carries
   `error=invalid_target`. (Without a resource the token is opaque, so L2.07 must keep both options.) Check x4.
5. **Dynamic registration needs `clientRegistrationDefaultApplicationType: "infer"`.** Real MCP clients register
   `http://localhost:<port>/callback` and send no `application_type`; the default `web` refuses any http redirect
   (`invalid_redirect_uri: web clients require https redirect URIs on non-loopback hosts`, and it did not treat
   `localhost` or `127.0.0.1` as loopback). With `"infer"` the registration is accepted as native. Unauthenticated
   registration is on (`allowUnauthenticatedClientRegistration`), as MCP needs.
6. **The MCP client completes OAuth headless as ada** (check 3a to 3c). The path: `POST /mcp` 401 with
   `resource_metadata` -> `GET /.well-known/oauth-protected-resource` -> `GET /.well-known/oauth-authorization-server/api/auth`
   (path-aware; the worker serves it from `oauthProviderAuthServerMetadata(auth)`; Better Auth natively serves only
   `/api/auth/.well-known/...`) -> `POST /api/auth/oauth2/register` -> `redirectToAuthorization` (captured) -> the
   authorize URL followed with ada's session cookie -> consent -> `finishAuth(code)` -> second connect with the token
   -> `tools/list`, `tools/call allowance.get` returns `{"person":"per_...","allowanceCents":1250}`. About 160 ms
   for the whole thing.
7. **Consent, exactly.** (a) A dynamically registered client always gets the consent step on first use, even with a
   signed-in session. (b) Followed without browser navigation headers, `GET /oauth2/authorize` answers `200
   {"redirect":true,"url":"/consent?...&sig=..."}`, not a 302; a headless follower must read the JSON `url` (and the
   same for the post-consent step). (c) Consent is accepted with `POST /api/auth/oauth2/consent` body
   `{"accept":true,"oauth_query":"<the consent URL's query string, sig included>"}` with ada's cookie, which returns
   `200 {"redirect":true,"url":"http://localhost:8899/callback?code=...&iss=..."}`. (d) The consent is remembered per
   client and person: a raw authorize for the same client without `prompt` returns the code straight away. But the SDK
   adds `prompt=consent` whenever `offline_access` is requested, so through the SDK the consent step appears again
   on every authorization (the test posts it again, and it passes). (e) With no session, authorize answers
   `{"redirect":true,"url":"/login?..."}`. (f) An unlisted `resource` comes back as an error redirect to the client's
   callback. (g) Default scopes on a registration without `scope` are `openid profile email offline_access`.
8. **Refused callers.** Bob (signed in, no row in `roles`) completes OAuth and gets a token; `allowance.get` returns
   `isError` with `forbidden: <bob> has no allowance-reader role` (the check is in the tool, on `sub`, so a token
   proves who, the role says what). No token: 401 with `WWW-Authenticate: Bearer resource_metadata="http://localhost:8802/.well-known/oauth-protected-resource"`.
   A forged JWT (right claims and `kid`, a fresh key): 401 `invalid_token`. Ada's real token with `sub` edited: 401.
   An opaque string: 401. Check 4, 5a to 5e.
9. **Device flow** (all under `/api/auth`, so `/api/auth/device/code`, `/device`, `/device/approve`, `/device/token`;
   `verificationUri: "/device"` is the page a person would open). `device/code` for `acme-cli` returns `device_code`,
   `user_code`, `verification_uri_complete`, 1800 s, 5 s interval (set to 1 s here); other client ids are 400. Before
   approval `device/token` says `authorization_pending`; polling faster than the interval says `slow_down`.
   `GET /device?user_code=` with ada's session claims the code for ada (it returns `status: pending`); bob's approve of
   it is 403; ada's `POST /device/approve` is 200; `POST /device/token` returns a bearer; with the `bearer` plugin
   `Authorization: Bearer <it>` resolves to ada through `auth.api.getSession` (`/me`); the code is single use. Check 6a to 6i.
10. **Footprint.** `wrangler deploy --dry-run` bundles to 3.5 MiB (611 KiB gzipped) with the SDK, Better Auth, the
    provider, jose and cfworker; compressed size is what a plan limit counts, and it is well under 3 MiB. No `node:` import failed under `nodejs_compat`. `CfWorkerJsonSchemaValidator`
    worked; the SDK still imports the Ajv provider statically (never constructed).

## The decision it supports

D3 #10 and #11 hold as written, with these edits:

- #11: add that the resource server verifies the JWT itself with `jose` against the same-origin JWKS (`createLocalJWKSet`
  over `auth.api.getJwks()`), checking `iss` and `aud`; no network call back to the auth server and no introspection.
  Role is checked in the tool, by `sub`, against the app's `roles` table.
- #11: dynamic client registration needs `clientRegistrationDefaultApplicationType: "infer"`, a declared `resources`
  entry, and the path-aware `/.well-known/oauth-authorization-server/api/auth` route in the worker.
- #10: the device endpoints live under `/api/auth/device/*`; the interval default is 5 s (`slow_down` if polled
  faster), so the CLI must honour `interval`.
- L2.07 and L2.08: a headless test must read the `{redirect,url}` JSON from authorize and consent, and post consent
  itself, as `scripts/flow.ts` does. The two web pages (`/login`, `/consent`) are required by the provider's config
  (`loginPage`, `consentPage`) even if only the portal ever renders them.

## Open risks

- Consent shows again on every SDK-driven authorization (Found 7d). Harmless headless, but a person sees the consent
  page on each reconnect from an SDK client; a `skipConsent` for a vetted client, or dropping `offline_access` from
  what the page offers, is a product decision for L2.07.
- Unauthenticated dynamic registration is open to anyone; it is how MCP discovery works, but the L2.07 step should cap
  it (the provider has `validateInitialAccessToken` and `clientRegistrationAllowedScopes`) and clean up stale clients.
- Only `scrypt` default hashing was run (about 130 ms); real workerd CPU limits (30 s default, 10 ms free plan) are
  not enforced locally. The sibling spike has a PBKDF2 fallback.
- Not tried: DPoP, `private_key_jwt`, key rotation on `jwt`, CIMD client discovery, the
  stateful (session id) transport, SSE responses (`enableJsonResponse: true` here).
- Local only: the cloud pass has not checked D1 remote latency for the `auth_jwks` lookup on every `/mcp` call (one
  read per request here; cache it in the isolate or via the Cache API if it matters).
