# The shared spec: one mini DAO, three chains

Every sub-spike (`evm/`, `solana/`, `aztec/`) builds **this** blueprint, so the differences between chains are
differences of the chain, not of the example. This is a spike: throwaway code, never imported by a package.

## The blueprint (as the developer would write it, K5's API)

```ts
// blueprint/things/proposal/thing.ts            code prefix "PR"
export const Proposal = Blueprint.thing({
  description: "A question put to the members, decided by one vote each.",
  fields: { id: ProposalId, digest: Digest, yes: Votes, no: Votes },
  lives: Blueprint.chain({ contract: "Governance", per: "workshop" }),
});
// machine: open (creates, -> "open"), vote ("open" -> "open"), close ("open" -> "passed" | "failed")

// blueprint/things/proposal/errors.ts             declaration order fixes the codes
export class AlreadyVoted   extends Blueprint.error({ proposal: ProposalId }, { exit: 3 }) {}   // PR-001
export class ProposalExists extends Blueprint.error({ proposal: ProposalId }, { exit: 4 }) {}   // PR-002
// generated by the machine: ProposalNotOpen { state }  ("absent" if never opened)          // PR-900
// generated by the runtime: NotAllowed (role check failed: not admin / not a member)        // AR-001
// K5's sketch also declared NotAMember next to `allowed: [member]`; the role check already refuses a non-member
// with NotAllowed, so NotAMember could never fire. It is dropped here (a K7 finding).

// operations (all runs: "chain")
proposal.open  { proposal: ProposalId, digest: Digest }        allowed: [admin]   move: open   emits ProposalOpened { proposal, digest }
proposal.vote  { proposal: ProposalId, choice: "yes" | "no" }   allowed: [member]  move: vote   emits VoteCast { proposal, choice, yes, no }
proposal.close { proposal: ProposalId }                        allowed: [admin]   move: close  emits ProposalClosed { proposal, passed }
member.add     { member: Address }                             allowed: [admin]                emits MemberAdded (public chains only)
proposal.get   { proposal } -> { digest, yes, no, state }      a read
```

Types: `ProposalId` = 32 bytes (or u64 where a chain makes that natural; say which), `Digest` = 32 bytes (keccak or
sha256 of the frozen revision body; on Aztec a Field), `Votes` = u32/u64.

**The four facts the war game must hold on every chain:**

1. A member votes once per proposal. A second vote is refused, and the refusal reaches TypeScript as a typed
   `AlreadyVoted` carrying code `PR-001`.
2. The tally (`yes`, `no`) is public.
3. Publishing links a D1 revision to a **confirmed** on-chain `ProposalOpened { proposal, digest }` event: a follower
   sees the event, waits for the chain's notion of confirmed, and matches `digest`.
4. On Aztec only: membership is private (nobody learns who the members are or who voted), a one-use claim (nullifier)
   scoped to the proposal stops the second vote, and the tally is public.

## Shapes to show, per chain (each is evidence for one of K7's eight questions)

- **Q1 surface.** The generated-shaped program: one entry per declared operation, wrapping a developer-written body,
  plus at least one *helper* the developer adds (a public/view helper and an internal one). Dump the machine-readable
  interface (ABI / IDL / Aztec artifact) and write a tiny script that classifies every entry as *operation*,
  *declared read*, *helper outside the surface* or *undeclared* against the operation list above. Note what the chain's
  interface does and does not carry (names, selectors, discriminators, account lists, visibility).
- **Q2 someone else's contract.** Deploy or load one existing third-party program on the local chain (EVM: an ERC-20;
  Solana: SPL Token; Aztec: the stock `Token` from `@aztec/noir-contracts.js`). Use it two ways: (a) as a *source* the
  TypeScript side reads through an adapter typed from its ABI/IDL/artifact (calls and events), and (b) as something
  our own program calls (membership gated by holding one unit of it, or say why that doesn't work on this chain). Note
  how its errors and events come back and what can't be typed.
- **Q3 signer vs submitter.** Show who signs and who pays: EVM both a direct wallet transaction and an EIP-712
  signature relayed by another key; Solana a relayer as fee payer with the member as a second signer; Aztec the
  member's own PXE proving, with sponsored fees. Say what `submission.confirmed` should mean on that chain, from what
  you observed.
- **Q4 state.** Where each fact lives (storage slots / accounts and PDAs with rent / notes and nullifiers), and what
  the client must know or supply to call an operation (EVM: just the address; Solana: every account; Aztec: notes in
  the PXE, sync first).
- **Q5 refusals.** How `AlreadyVoted`, `ProposalExists`, `ProposalNotOpen` and `NotAllowed` are raised, what the client
  receives raw, and how it decodes to the typed class with its stable code. **Find what makes a code unstable** (a
  rename, a field change, a reorder) and what refusals arrive with no code at all (e.g. a runtime error instead of our
  own).
- **Q6 events and confirmation.** How the follower reads `ProposalOpened` and `VoteCast`, the chain's confirmation
  levels, and what a reorg/rollback looks like locally (force one where the local chain allows).
- **Q7 local world.** Start time, ports, what's real and what's faked locally (proof verification on Aztec in
  particular: try to run the local network *with* client proof verification on and show a tampered or invalid proof
  rejected; say exactly what was and wasn't verified).
- **Q8 cross-check.** A small seeded random-sequence test: the reference TypeScript machine in `../reference.ts`
  (import it, don't copy it; `sequence(seed, n)`, `expected(steps)`, `SEEDS`; actor 0 is the admin, 1..3 get added,
  4..5 are outsiders; proposal ids 1..4, digests 1..1000) and the chain program run the same sequence of open / vote / close / add-member calls
  from random callers; after each step both agree on state, tally and refusal code. Fixed seeds, a few hundred steps
  (fewer on Aztec where each step proves; say how many and how long).

## Rules

- Local chains only. No cloud, no testnet, no paid service. No private key or mnemonic printed, written to a file or
  committed (use the local chain's well-known dev accounts by index, or generate in memory).
- Pin every version exactly; use only releases published at least three days before today (18 November 2026). Record
  exact versions and their release dates in `versions.json`.
- Ports: EVM uses 18545; Solana uses 18899 (RPC) and 19900 (faucet) and its gossip range above 18000; Aztec uses the
  noir spike's defaults (8080, 8545 for its L1). Stop every process you start, on success or failure.
- Put everything under your own folder. Big tool installs go under `<your folder>/tools/` (git-ignored) or the
  tool's normal user-level location; say which.
- Retain evidence as files under `<your folder>/evidence/` (command output, decoded errors, measured times).
- End with `<your folder>/README.md`: question, what was tried, what was found (numbered, each marked validated /
  refuted / not tested, with file:line or evidence links), the decisions it supports, open risks, and how to
  reproduce.
