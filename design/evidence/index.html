I wrote `implementation/handlers/allowance/spend.ts`, and `architect check` passes (types, rules and drift). I haven't run `architect prove --env local`, because I have no tool for it. So the 9 evals and the three journeys are untested.

The handler works like this:
- **Load:** it loads the allowance through `steps.load(...)` and works out what is left (`limit - spent`).
- **Refusal:** if the amount is more than what is left, it logs why with `Effect.logInfo` and refuses with `AllowanceExceeded`, carrying the remaining amount.
- **Record:** otherwise it writes the new `spent` total through `steps.record(...)`.
- **Move:** it then calls `move("exhausted")` if nothing is left, or `move("active")` if not.
- **Answer:** it returns `{ remaining }`.

I didn't handle `AllowanceNotActive` or `NotAllowed`; the runtime refuses those before the handler runs.

I couldn't find documentation for the `Records` API. I assumed `records.update(Allowance, id, { spent })` exists, based on how `grant.ts` and `accept.ts` use `records.insert` and `records.find`. Check passed with it, so it type-checks. Whether it behaves correctly is what the prove run will show.

L1.21 Errors and the logs that decide them done

A refusal now carries the log line that decided it. While the handler runs, a second logger sits beside the project's and remembers the last thing logged; when the handler refuses, that line goes on the operation's span as refusal.log.
