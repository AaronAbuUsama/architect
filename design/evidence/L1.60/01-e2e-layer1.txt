I wrote `implementation/handlers/allowance/spend.ts`, and `architect check` passes (types, rules, drift all clean). I haven't run `architect prove --env local`, so the 9 evals and the three journeys are untested. I don't have a tool for that command.

How the handler works:
- **Load:** it reads the allowance through `steps.load(records.find(...))`. If the record is missing it dies, the same way `invitation/accept.ts` does, since the runtime has already found it.
- **Refusal:** if `amount` is more than what is left (`limit - spent`), it logs why with `Effect.logInfo` and fails with `AllowanceExceeded({ remaining })`. The role check and the machine's `AllowanceNotActive` check are left to the runtime.
- **Record:** it writes the new `spent` through `steps.record(records.update(...))`, then calls `move("exhausted")` if nothing is left and `move("active")` otherwise.
- **Answer:** it returns `{ remaining }`, the amount left after this spend.

I couldn't read the `Records` API, so I guessed `records.update(Allowance, id, { spent })`. The type check accepts it, but I haven't seen it run. The other thing to confirm is that `steps.record(...)` wrapping the update (rather than the move, as `revoke.ts` does with `steps.update(move(...))`) satisfies the step eval. If `prove` shows a problem with `spent` not updating or with the steps, those are the two places to look.
