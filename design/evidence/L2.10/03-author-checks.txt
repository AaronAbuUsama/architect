=============== pooled-socket-note.txt
A hazard in the author's check 08 (and any check shaped like it), found while running its portal half. Not the portal's: any route shows it.

The check calls `portal(url)` (a `fetch`) at its start, then runs only `spawnSync` steps (seed, replay, watch, build, promote, prove), which block the
Node event loop, and calls `portal(url)` again at its end. `promote --to staging` restarts staging in between: the old workerd dies, a new one listens on
the same port. Node's fetch (undici) kept the first request's connection in its pool, and with the loop blocked it never saw the server close it, so the
second fetch is written to a dead socket: `TypeError: fetch failed`, cause `write EPIPE` or `read ECONNRESET`.

Reproduced with the plain `/_architect/bundle` and with `/portal`, on a copy of acme: fetch, `env down`, `env up` on the same port, no async wait, fetch again:

  FIRST 200 {"content-encoding":"gzip","content-type":"application/json","transfer-encoding":"chunked"}
  SECOND (pooled) FAILED TypeError: fetch failed Error: read ECONNRESET
  THIRD (connection: close) ok 200

With an async wait of 8 s between (the loop free to see the close) the pooled fetch works. A Worker cannot prevent it: a `Connection: close` header on its response
is dropped by workerd (the first response's headers show none). The cure is in the check: `fetch(url, { headers: { connection: "close" } })`, or a dispatcher
without keep-alive. The private copy of the portal half used under `tmp/` does the first.
