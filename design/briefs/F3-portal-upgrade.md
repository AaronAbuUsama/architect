## The shape (decide the open parts in your first commit, as a decision record)

Settled, don't reopen:
- The portal stays a route of each environment's own Worker (D3 #130): `/portal` for people, `/_portal/v1/*` for
  data. No new daemon, no `env up portal`. The same bundle runs everywhere.
- One source of truth for evidence: the snapshot (`/_portal/v1/snapshot`, built by `Snapshot.take` over the logbook,
  D3 #132 and #133). The static pages never hold a verdict. Only `recorded-pass` is a tick; nothing unread is green;
  the logbook's address is in no page and no JSON (D3 #131).
- The wire stays schemaVersion 1. Additions go in `extensions` or as additive schema keys. A change to a core meaning
  is not yours to make here.
- Open source only. No HeroUI Pro anything in this repository: no `@heroui-pro/*` dependency, source, archive,
  screenshot or token. HeroUI Pro is a separate face on draft PR "Portal Pro" (branch build/portal-pro), parked; it
  will read the same `/_portal/v1/*` data later. HeroUI OSS 3.x is allowed if a component earns it.

Open, yours to decide, with a recommendation each (record the call in design/decisions/F3-portal-site.md):
1. How live evidence reaches a static page. Recommended: the Worker fills marked slots in the static HTML per request
   from the same snapshot (HTMLRewriter is native to workerd), so a reader with JavaScript off, and check 08, see the
   real state; a small script may then refresh from `/_portal/v1/snapshot?digest=<the page's digest>` and reload on
   409. Alternatives: client-only fetch (fails check 08 and no-JS readers), or keep today's server-rendered `/portal`
   home beside static pages (two faces to keep consistent).
2. Where the build-time toolchain lives. Recommended: a new build-time package (for example `@architect/portal-site`,
   `env:build`, never imported at runtime) that the generator or `architect build` runs to turn blueprint.json and the
   docs into static files; `@architect/portal` keeps only serving: assets, slot filling, the JSON routes. The rule
   "compiler and generators never run in production" holds; the Worker imports no React.
3. Where the output goes and whether it is committed. Recommended: built into the bundle (Workers static assets), not
   committed under generated/, so the repository holds no built HTML; whatever is committed opens with the generated
   header (`<!-- Generated from … Do not edit. -->` for HTML).
4. The stack. Recommended: F1 §5's React Router prerender with Fumadocs core/UI and a custom `loader()` source of
   virtual pages made from the blueprint, plus static search. Fumadocs inside a non-Fumadocs shell is unverified: if it
   fights you, say so in the record and pick the smaller working path.
