# D3: destinations, versions, secrets, and how layer two ships on this Mac

Decided 16 November 2026 by the builder (Aaron gave architectural ownership). Evidence: `design/wayfinding/stage-3.md`
(research R1 to R4, run that day from primary sources at the pinned versions, with live experiments on workerd).

## The build plan's three recommendations stand

1. **Versions come from the model diff.** An added operation or read is minor. A changed payload, answer or error
   set is major. A budget or docs change is a patch. `architect version --next` prints the release version (`1.1.0`).
   Staging publishes prereleases of it (`1.1.0-next.<n>`, dist-tag `next`); production publishes the version itself.
2. **Secrets are named per environment.** `blueprint/environments/<env>.ts` declares secret names only. Locally their
   values are generated into `.architect/environments/<env>/secrets.env` (mode 0600), never on a command line, where
   `ps` would show them. In the cloud pass Alchemy sets them as Cloudflare secrets.
3. **Verdicts live in the logbook.** It is a Durable Object behind one worker, with R2 for each revision's model. On
   this Mac it is a long-lived local environment of its own.

## How shipping runs locally (stage 3)

4. **A local environment is a long-lived workerd, driven by wrangler.** Each of test, staging and production runs
   `wrangler dev` on its own port, with its own `--persist-to` state, config folder and `--inspector-port 0`, and its
   state survives a restart (R1 measured both). `architect env up|down|status` keeps a pidfile and a port per
   environment under `.architect/environments/`, and waits for wrangler's ready line.
5. **Alchemy waits for the cloud pass.** Its local mode is a foreground dev session on its own workerd, not a deploy;
   its `deploy` and `destroy` always need a Cloudflare account; its v2 line is weekly-changing beta (R1). So
   `generated/infra` holds the per-environment wrangler configs now, and gains the Alchemy stack, deploying the same
   bundle, when the cloud pass turns the `cloudflare` destination on. Until then that destination says it is not
   built.
6. **One artefact per revision.** `wrangler deploy --dry-run --outdir` builds `main.js` once, with no credentials;
   two builds of the same source hash the same (R1). The bundle is kept at
   `.architect/artefacts/<revision>/main.js` with its sha256, and every environment runs that file unchanged
   (`no_bundle: true`). The worker reports the hash, so `promote` can show that production runs what staging proved.
7. **Test worlds have a lifetime.** A test world's Durable Object sets an alarm at creation and destroys the world at
   expiry: `deleteAll`, its D1 rows and its R2 prefix. Alarms fire and survive restarts under local workerd, but only
   while a workerd runs (R1), so `architect worlds reap` starts the test environment to let past-due alarms fire. In
   CI each pull request gets `test-pr-<n>`, destroyed in an `always()` step.
8. **Signed verdicts.** The logbook accepts a verdict only with an OIDC token for audience `architect-logbook`,
   verified with `jose` 6.2.15 against the one issuer its environment names, RS256 only, with repository, ref and
   workflow checked. In GitHub CI that is GitHub's own issuer (`token.actions.githubusercontent.com`, the job given
   `id-token: write`). On this Mac it is a real OIDC server, `ghcr.io/navikt/mock-oauth2-server:6.1.4` (digest
   `sha256:647dd8c7…0192`), whose clients are scenarios (`ci-main`, `ci-other-branch`). A forged token, a token from
   another issuer and no token are each a 401 (R2 measured all three on workerd). A deployed environment may name
   only an `https` issuer; the environment check fails the build otherwise. Fork pull requests get no token, so they
   can't post verdicts. The `ci-oidc` spike proved this on GitHub's runner (`spikes/ci-oidc/`): the job's real token verified
   against the live JWKS on push and on a pull request, and the same worker passed the same cases against the local
   issuer, with only env vars changed. A pull request's `ref` is `refs/pull/<n>/merge` and its `sha` the synthetic merge
   commit, so the logbook takes `ALLOWED_REFS` as an allow-list of patterns (`refs/heads/main`, `refs/pull/*/merge`,
   `*` one path segment, never a prefix), checks `job_workflow_ref` as well as `workflow`, stores `ref` and
   `event_name` with every verdict, takes the revision from the job's own field rather than `sha`, and lets only
   `main` verdicts feed release gates.
9. **Publishing stays on the machine.** The SDK and CLI publish to Verdaccio, with explicit no-proxy rules for the
   project's own names (the unscoped `acme` exists on npm), always with `--tag next` for a prerelease (pnpm silently
   tags it `latest` otherwise), and installs name the exact version (R3). CLI binaries are Node single executables:
   an esbuild CommonJS bundle injected with `postject` 1.0.0-alpha.6 into the official Node 24.22.2 binary for each
   target (macOS arm64, Linux x64). The Homebrew tap is a local git repository whose formula points at `file://`
   tarballs with their sha256, installed by its full name so Homebrew's tap trust covers just that formula, then
   uninstalled and untapped. The `single-binary` spike proved this (`spikes/single-binary/`): both binaries built on
   this Mac, about 125 MB each and starting in 0.12 s, installed through a local tap and ran, on macOS with a valid
   ad-hoc signature and on `ubuntu-latest`, where Homebrew left the ELF untouched (`skip_clean` is kept as insurance).
   What ships as a binary in layer two is the generated project CLI (`acme`), a client of the API. Architect's own CLI
   is not yet safe as a single executable: it spawns `process.execPath` as Node for the compiler, reads `import.meta`
   at load, and resolves the lint plugin and wrangler as files, so it stays an npm package until that is reworked
   (`later.md`). A downloaded macOS binary also wants a Developer ID signature and notarization, which is the cloud
   pass's, with Aaron's credentials. GitHub releases are the cloud pass's switch: `gh release create` with the same
   tarballs and `SHA256SUMS`, and the formula's `url` the only difference.
10. **Sign-in in deployed environments is Better Auth's.** The CLI signs in by device code with Better Auth 1.7.15's
    `deviceAuthorization` plugin (client `acme-cli` only, table `auth_device_code`). A test approves as ada without a
    browser: it claims the code with her session, then approves it (R4). The CLI honours the returned polling `interval` (faster
    polls get `slow_down`); another person approving ada's claimed code is a 403, and a device code is single-use
    (`mcp-oauth` spike).
11. **The remote MCP server is one stateless worker route.** `@modelcontextprotocol/sdk` 1.32.2's web-standard
    streamable HTTP transport, a fresh server per request, the Cloudflare JSON-schema validator (workerd forbids
    Ajv's generated code). OAuth 2.1 comes from `@better-auth/oauth-provider` 1.7.15 with the `jwt` plugin, on the
    same D1 as sign-in, so a token's subject is the same principal and the existing role check refuses a call. No
    Durable Object is needed. Cloudflare's `McpAgent` is feature-frozen and keeps tokens in KV (R4). The `mcp-oauth` spike proved it on local workerd and D1
    (`spikes/mcp-oauth/`, 33 checks), and fixed these details: the MCP route verifies the JWT itself with `jose`
    against Better Auth's JWKS, checking `iss` and that `aud` contains the MCP URL; dynamic registration needs
    `clientRegistrationDefaultApplicationType: "infer"` (the default refuses `http://localhost` callbacks, which real MCP
    clients register); the MCP URL is listed in `resources`; the worker serves the path-aware
    `/.well-known/oauth-authorization-server/api/auth` itself; the `jwt` plugin's own `/token` is disabled; open
    dynamic registration gets a cap. A dynamically registered client sees consent every time it asks for
    `offline_access`, and headless authorize answers `{redirect, url}` JSON rather than a 302, so the checks follow
    it and post consent.
12. **`watch` reads the local OTLP sink.** The same evals, without journeys and without coverage, run over what the
    Collector recorded from an environment's traffic. Axiom is the cloud pass's sink, behind the same reader.
13. **The portal is a read-only site on workerd,** reading the logbook: the blueprint, the docs, the verdicts per
    environment and what is stale.

## Spikes, before the steps that need them

- `mcp-oauth`: on local workerd, `oauthProvider` with the `jwt` plugin on `AuthD1`. Do its tables create, does JWT
  signing work, is a JWT access token issued for `resource=<mcp url>`, and how does consent go for a signed-in
  session? Then an MCP client completes OAuth headless as ada and calls one tool.
- `single-binary`: a Linux x64 SEA cross-built on this Mac from Node 24.22.2, run on `ubuntu-latest`, and installed
  through a local tap there (with and without `skip_clean`); the macOS arm64 one installed through the tap, its
  signature still valid.
- `ci-oidc`: on a throwaway branch, a job with `id-token: write` mints a token for `architect-logbook`, posts it to a
  workerd logbook on the runner, which verifies it against GitHub's real JWKS. Records the claims on a same-repo pull
  request.

## The command surface and Gate 2's checks

14. **Commands layer two adds** (each prints the lines below; the checks match them).
    - `architect env up|down|status <env>` starts, stops and reports a long-lived local environment (`staging`,
      `production`, and `logbook`, the logbook's own worker). `up` prints `<env> up http://127.0.0.1:<port>`.
    - `architect build` builds the revision's bundle once: `built <revision> sha256:<hash>`. The revision is the git
      commit (`git rev-parse --short HEAD`); a project outside git can't build.
    - `architect prove --env test` makes world `test-<id>` in the test environment with the environment's lifetime
      (`ARCHITECT_LIFETIME` overrides it for checks), runs the journeys and evals, posts a signed verdict per operation
      to the logbook, and destroys the world: `world test-<id> · expires in <lifetime>`, then
      `verdicts <op> ✔ …   (revision <rev>)`, then `world destroyed`. `architect worlds reap` destroys every world past
      its lifetime: `reaped <n>`.
    - `architect version --next` prints the release version worked out from the last production release's model in
      the logbook (`1.0.0` when there is none). `architect impact` adds `next <version>` and, once there are verdicts,
      `stale <ops> in <envs>` from the logbook.
    - `architect promote --to staging` deploys the revision's bundle (server, mcp, portal), publishes the SDK and CLI
      prereleases, proves against staging and posts its verdicts. `architect promote --to production` refuses a
      revision without all-green staging verdicts (`refused: <rev> has no green verdicts in staging`, exit 1), and
      otherwise deploys the same bundle (`production from staging <rev> sha256:<hash>`) and publishes the release.
      Destinations the local pass can't reach print `skipped <destination> (cloud pass)`.
    - `architect watch --env <env>` runs the evals over the environment's recorded telemetry:
      `<op> p95 <n>ms (budget <n>ms) ✔|✘`, `refusals: <Error> <n> …`, and `drift <ops>|none`.
    - The generated CLI gains `acme session sign-in --env <env>` (device code; prints the code and the URL to approve
      it at) and `acme --version`.
15. **Gate 2 is `nx run e2e:layer2`, eight checks,** replaying walkthrough steps 9 to 12, each on a copy of acme under
    git, with the local issuer, Verdaccio and the local tap:
    1. `prove --env test`: a test world with a lifetime, a signed verdict per operation, the world destroyed; a run
       killed mid-way leaves a world that `worlds reap` removes after its lifetime.
    2. The logbook takes a verdict signed by the trusted issuer and refuses a forged one, one from another issuer and
       an unsigned one, each with 401.
    3. Adding `allowance.list` (`architect add read`, then the docs' `list.ts`) gives `next 1.1.0` and `stale none`,
       and `allowance.list 9 evals ✔`; loosening spend's budget makes exactly spend stale in staging and production.
    4. Promotion: production refuses a revision with no staging verdicts, then takes the one staging proved, running
       the same bundle hash; the first release is `1.0.0`, the release after the read is `1.1.0`.
    5. Publishing: `@acme/sdk` installs from Verdaccio at exactly `architect version --next`, and
       `brew install <tap>/acme` from the local tap runs `acme --version`, printing that version.
    6. Device sign-in: `acme session sign-in --env staging`, approved by ada without a browser, then
       `acme session show` prints her.
    7. MCP: a client completes OAuth as ada and calls `allowance.get`; a person without the role is refused.
    8. Watch and the portal: replayed staging traffic gives p95 against budget and refusal counts; a planted slow
       handler shows as drift; the portal shows `allowance.spend` `test ✔ staging ✔`, and after a budget edit `stale`
       on spend only.
16. **The author's contract stands, and its seven gaps are settled here.** The ✍️ author's checks in `e2e/layer2/`
    fixed the details #14 left open; each is commented at the top of its check, and the build follows them:
    configuration from `ARCHITECT_*` environment variables, `env up <env> --port <n>` with a pidfile (building the
    revision when it has no artefact), the logbook's `POST /verdicts` and `GET /verdicts?revision=&environment=`,
    `GET /_architect/bundle` answering `{revision, sha256}`, the portal at `/portal`, the MCP route at `/mcp` with
    tools named as operations. The gaps:
    1. `Blueprint.read` gains `where`, `order` and `page` (L2.04), answering `{ items, next }`, as the docs' `list.ts`
       has them.
    2. The generated `acme session sign-in` keeps email and password against a local world; with `--env <env>`, for
       an environment whose identity is Better Auth, it is the device flow. The session is stored in
       `ACME_CONFIG_DIR` (default the user's config folder), and `session show` reads it.
    3. Better Auth is mounted at `/api/auth`; the device claim and approve shapes are as the author wrote them, which
       the `mcp-oauth` spike confirmed. The MCP check follows the `{redirect, url}` JSON and posts consent.
    4. A token naming a ref outside `ALLOWED_REFS` is refused like any other bad token (401).
    5. The generated SDK's `@architect/*` dependencies are published to the same Verdaccio by the check's setup, as
       Gate 1's check 1 does, so `npm install @acme/sdk@<next>` resolves everything from the local registry.
    6. Layer 1's and layer 2's checks run one after the other locally, and as separate CI jobs.
    7. `env up` builds the revision when its artefact is missing.

## L2.01: how the local reading was built (16 November 2026, the builder)

Evidence: `design/evidence/L2.01/` (the tests, and a demo of build, env up, bundle and env down).

17. **An environment's wrangler config is run state, so it lives in `.architect/environments/<env>/wrangler.jsonc`, not
    in `generated/infra/`.** It carries the revision's hash, an absolute path to the artefact and the environment's name,
    so it changes with every build and every machine. `generated/` is committed and drift-checked (`nx sync:check`),
    and a file there that changes per run would fail the check. `env up` writes it from `generated/server/wrangler.jsonc`
    (source swapped for the built `main.js`, `no_bundle: true`, worker and database named `<name>-<env>`, vars
    `ARCHITECT_ENVIRONMENT`, `ARCHITECT_REVISION`, `ARCHITECT_BUNDLE_SHA256`). `generated/infra/` stays reserved for the
    cloud pass's Alchemy stack. This amends the last sentence of #5, which put the per-environment configs there.
18. **`build` and `environments` are modules of `packages/prove`, and the long-lived process is `Worlds.launch`.** An
    environment is a world that stays up, so it reuses the world module's wrangler code: one place for the
    retry-on-a-taken-socket, the ready check and `--inspector-port 0` (now on prove's worlds too, closing R1's shared
    9229 pitfall). `launch` starts wrangler detached in its own process group and hands back the pid; `environments`
    keeps the pid, so `down` stops the group (wrangler and workerd), asking first and insisting after ten seconds. The
    pid file is written the moment the process exists, so a run killed part-way can still be cleaned up by `down`.
    `cli` is only the composition: `main.ts` prints and sets the exit code.
19. **`up` is "make it run, leave it alone if it already does".** A running environment is returned as it is. With
    `--revision <rev>` it is restarted onto that artefact with its state kept (what `promote` will use, L2.05); an
    explicit revision with no artefact is an error, and an implicit one builds. The port is `--port`, else the one it
    last had, else any free port; an explicit port that is taken is refused at once rather than left to wrangler. `down`
    and `status` need no declared environment, so `env down logbook` works whatever else is true. `up` refuses `local`
    (that is `dev` and `prove`) and `logbook` (its own worker, L2.03: `OWN_WORKER` in `environments/service.ts` is the
    seam) with a message that says so. The logbook's `worlds <n>` line for `status test` is L2.02's, appended there.
20. **Secrets go in `secrets.env` (mode 0600) and reach wrangler as `--env-file`.** Checked on wrangler 4.156.1: it
    prints "Using secrets defined in secrets.env" and binds each name as a hidden variable, so nothing shows in `ps` and
    nothing is in the generated config (the test checks both). `AUTH_SECRET` is built in; the names an environment
    declares (`generated` and `stored` alike) get a value generated locally, once, and kept across restarts so sessions
    stay valid. D3 #2 named the file `secrets.env`; this is how it is read. Prove's worlds still pass their throwaway
    `AUTH_SECRET` as `--var`: it is fresh each run and never a real secret, but it shows in `ps` and could move to a file
    when someone needs it to.
21. **`GET /_architect/bundle` is in the generated server,** answered before the app is built, from `ARCHITECT_REVISION`
    and `ARCHITECT_BUNDLE_SHA256`: `{ "revision": …, "sha256": … }` with the bare hex. A world made by `dev` or `prove`
    has neither var and answers 404 `NotAnEnvironment`, so the route says "I am an environment" and nothing else. `env
    up` is ready when this route answers.
22. **Environments are read into the model by their path.** `blueprint/environments/<name>.ts` is the environment
    `<name>`; the declaration carries no name (`Blueprint.environment({ … })`, as the docs' layer-two files have it),
    and the compiler puts it in `model.environments`, present only when the folder exists, so projects without one are
    unchanged. The compiler refuses a `promotesFrom` that names no other environment file, a secret that isn't
    `UPPER_SNAKE_CASE`, a `lifetime` that isn't a duration, and a `deploy` or `publish` with no `cloud`. The model holds
    secret names and how they get values, never a value. `deploy` keys are `server`, `mcp`, `portal` and `publish` keys
    `sdk`, `cli`, typed, so a misspelling is a type error; layers four and five add `chain`, `clock`, `contracts`,
    `keeper`.
23. **`architect.config.ts` is declared and type-checked, and the compiler does not read it yet.** `Blueprint.config`,
    `Auth.betterAuth` and `Telemetry.otlp` exist and acme has the file as the docs show it. Nothing generated depends on
    it until the MCP server and the portal are outputs (L2.06, L2.08), and putting it in the model now would make
    `generated/model/model.json` differ between acme and the Gate 1 and Gate 2 checks' copies of it, which copy
    `blueprint/` but not the root file (`copyOf` in `e2e/layer1/support.ts`). When L2.06 gives it a consumer, the
    checks' copy list needs `architect.config.ts` (the author's call: I may not edit `e2e/`).
24. **The starter carries the four environment files and not the config.** The preset copies `blueprint/` as it is, so
    new projects get `local`, `test`, `staging` and `production` for free. The starter's staging and production name no
    domain, no tap and no `mcp` or `portal` (those are acme's, and a new project has no `acme.dev`); each carries a comment
    saying where a domain goes. `architect.config.ts` needs the project's name and so a template; it waits for its
    consumer (#23).
25. **`build` keeps `bundle.json` beside `main.js`, and says when the tree is dirty.** `Build.find` rehashes the file
    against the record, so an altered artefact is an error and not a silent run. A build whose working tree differs from
    the commit prints `warning: …` on stderr, because "the same revision, the same hash" holds only for a clean tree;
    it still builds, because refusing would stop a developer building before committing; `promote` (L2.05) is where a
    bundle of uncommitted source should be refused. The build never
    sees `CLOUDFLARE_*` credentials: they are removed from its environment.

## L2.03: the logbook (decisions #30 on; #17 to #29 are the L2.01 builder's)

Built 16 November 2026 in `packages/logbook`; evidence in `design/evidence/L2.03/`. These settle what #3, #8 and #16 left open.

30. **One worker, two stores.** `Book` is a SQLite Durable Object, always the one named `book`, holding every verdict and
    the production releases. Each revision's model is one R2 object, `models/<revision>.json`. Nothing carries a clock:
    `seq`, an autoincrement id, orders the ledger, so "latest" is the highest `seq`. The worker is `src/main.ts`; its
    `wrangler.jsonc` binds `BOOK` and `MODELS` and sets no policy variables, so a missing variable is a 500 that names it.
31. **The API.** Writes need the bearer token (401 first, before the body is read, and nothing is stored); reads are open.
    `POST /verdicts` takes `{revision, environment, operation, verdict}`. `GET /verdicts?revision=&environment=&operation=&ref=`
    answers an array, oldest first, each row with `seq`, `repository`, `ref`, `workflow`, `event_name` and `sha` beside the
    four posted fields. For L2.04 and L2.05: `GET /verdicts/latest?...` is the newest verdict of each operation in each
    environment among those matching (ask with `ref=refs/heads/main` for what may feed a release gate; a pull request's
    verdict then never hides main's). `PUT /models/<revision>` stores the model; the same model again is fine, a different
    one is 409, so a revision's model never changes; `GET /models/<revision>` is open. `POST /releases` takes
    `{version, revision}` and needs the revision's model to be there (409 otherwise) and the version to be new (409);
    `GET /releases/latest` is the last production release, or 404. A body that doesn't fit its schema is 400; a revision
    is `[0-9A-Za-z][0-9A-Za-z._-]{0,99}` because it becomes an R2 key.
32. **`job_workflow_ref` is checked when the token has one, and the author's token need not.** The author's local
    scenario (`e2e/layer2/services.ts`) carries `repository`, `ref` and `workflow` but no `job_workflow_ref`, and GitHub's
    always does. So: when present, its repository must be `ALLOWED_REPOSITORY` and its ref allowed by `ALLOWED_REFS`.
    `ALLOWED_WORKFLOWS` entries are names matched on `workflow`, and an entry with a `/` is a workflow file path matched
    on `job_workflow_ref` (`.github/workflows/prove.yml`), which two workflows cannot share the way they can a name. A
    deployed logbook should list the file path. `event_name` and `sha` are optional and stored as null when absent.
33. **How the CLI starts it.** `@architect/logbook` exports `Logbook.launch({ port, state, policy })`, which gives
    `{ command, args, env }` for a long-lived `wrangler dev` (its own `--persist-to` folder, `--inspector-port 0`, the
    policy as `--var`s, nothing secret); `Logbook.ready(url)` waits for `GET /health`; `Logbook.discoverJwks(issuer)` reads
    `jwks_uri` from the issuer's discovery document; `Logbook.start(...)` is all of that, scoped, for tests. `env up logbook`
    maps `ARCHITECT_OIDC_ISSUER`, `_REPOSITORY`, `_REF` and `_WORKFLOW` to the policy (refs `[ref, "refs/pull/*/merge"]`
    if a pull request's token should count; audience `architect-logbook`) and spawns `launch` detached with a pidfile.
34. **Tests.** The done-when check (`local/local.test.ts`) runs the real worker under `wrangler dev` 4.156.1 on ports
    8930 to 8949 with two `mock-oauth2-server` containers by digest (the trusted issuer and a second, rogue one): a
    forged token (real claims and `kid`, a fresh key), another issuer's token, a branch outside the allow-list, a ref that
    only looks like a pull request (`refs/pull/7/merge/../x`), another repository, workflow and audience, no token and
    not-a-JWT are each 401 with nothing stored; a trusted token's verdict reads back with its `ref` and `event_name`; the
    state, model and release survive a restart. Unit tests cover the policy (`tokens.test.ts`, with tokens signed by the
    test's own key: RS256 only, `PS256` refused), the SQL (`book.test.ts` on node's SQLite) and the routes (`http.test.ts`).
    Not exercised: a deployed worker and GitHub's live JWKS (the `ci-oidc` spike did that), and a non-`https` issuer is not
    refused by the logbook itself (D3 #8 puts that in the environment check).

## L2.07: real sign-in, the local reading (decisions #40 on)

Built 16 November 2026; evidence in `design/evidence/L2.07/`. These settle #10 and #16 item 2 as built. The real staging
sign-in is the cloud pass.

40. **The server.** `host-cloudflare/auth` adds Better Auth 1.7.15's `deviceAuthorization` to the plugins that were
    there (`bearer` already was, so the device token, which is an ordinary session token, resolves through the existing
    `Principals`): `validateClient` accepts only `AuthOptions.cli` (the generated server passes `<project>-cli`, so
    `acme-cli`; the default is `cli`, which keeps the evals' fixture servers valid), `interval` is 5 s (a faster poll is
    `slow_down`), `verificationUri` is `/device`, and the table is `auth_device_code`. The table comes through the schema
    path as every other: `scripts/auth-schema.ts` writes `internal/schema.ts`, applied `if not exists` on first use
    (the world and the server both do). That script now also makes `create unique index` idempotent: the device table's
    two unique indexes made the second isolate's schema batch fail with "already exists" (found by the test, as a 500).
    `AuthD1.handle(auth, request)` answers Better Auth's routes. The generated server routes `/api/auth/*` to it, before
    the Effect API, with its own instance (`routesOf`): the same D1 and secret as the layer's, so either one's sessions
    are people to both. A second instance and not one shared with the layer, because the author's `who-may-call` fixture
    is a byte-for-byte copy of the generated server minus its gate and its test allows five differing lines; changing
    the layer's line would have made six.
41. **The CLI's device flow is generated, self-contained code,** `generated/cli/src/session/device.ts`, and not a new
    package (the nine published packages stay nine; the CLI needs only Effect and its SDK). It posts `device/code` for
    `<project>-cli`, prints `code <user code>` and `approve at <url>`, polls `device/token` with an Effect `Schedule`
    (`Schedule.fromStep`: the server's `interval`, plus 5 s after every `slow_down` as RFC 8628 says), gives up when the
    code's `expires_in` passes (`DeviceRefused {"error":"expired_token"}`, exit 1), keeps the session and prints
    `signed in`. No plain sleep; no password or token is ever printed. The URL to approve at is the server's path and

## L2.04: a read that lists, versions from the model, staleness from the logbook (16 November 2026, the builder)

Evidence: `design/evidence/L2.04/` (the tests, the commands against a real logbook, and check 3's state). These settle #1, #14 and #16 gap 1.

60. **A read lists: `where`, `order`, `page`; it answers `{ items, next }`.** `Blueprint.read(Thing, { where: [fields…], order:
    "newest" | "oldest", page: n, allowed, budget })` is a second form beside `by: "id"`, which is unchanged. The payload is the
    `where` fields (the thing's own `Field`s, so a role can follow them: `owner.of("organization")`) plus an opaque `cursor`, every one
    optional, and `state` may be a filter when the thing has a machine. The answer is a page, `{ items, next }`: each item is the whole
    instance with `state` as text (`"none"` before a first move), and `next` is null on the last page. Order is the order rows were made in
    (SQLite's `rowid`; `newest` is the last made first), never a clock, and the cursor is the last row's `rowid`, so a page is a keyset and
    rows made meanwhile never shift one. The server enforces roles as for any read, on the thing a filter names, so a caller with no filter
    the role is decided on (no `organization`) is refused `NotAllowed`; a cursor the read did not hand out is refused the same way. The
    type of a list's payload makes every filter optional (`ListPayload`): the role, not the type, requires `organization`. The compiler
    refuses a list of a thing that lives as actors (one instance each, nothing to scan), `where: ["state"]` on a thing with no machine, and a
    `page` outside 1 to 1000. The model gains `OperationModel.list` (`where`, `order`, `page`, present only for lists) and
    `FieldModel.optional` (present only when true), so models of projects with no list are byte for byte as before. `Store` gains `list`
    (D1: one `SELECT` with one row more than the page, in `host-cloudflare/store/internal/list.ts`; the in-memory store has it too).
    Generated: the api, server and sdk follow the declaration's own schemas unchanged; the CLI makes optional payload fields `Flag.optional`
    and drops the ones left out (`supplied`, in `output.ts`, so the other commands' files don't change); the docs say a read is a page,
    mark optional fields and show `[--flag <flag>]`.
61. **No new eval; the nine cover a read.** A list is covered like `get`: every call's answer shape is checked, refusals against the
    declared set (`NotAllowed` only), who may call decided from the world's facts by the same `Access` the server uses, performance against
    the budget, and coverage by being called. The one change is in `answer shape`: a span keeps an object answer as JSON text, so a field
    declared by its schema (`items`, `next`) is read back from it (only text that starts `[`, `{` or is `null`; a cursor like `"2"` stays text).
    `allowance.list 9 evals ✔` passes on the author's journey and on a journey of my own that pages three allowances two at a time.
62. **Version rules, as code (`Compare.release`).** Operation added: minor. Operation removed: major. Operation changed: major if its
    `payload`, `answer`, `errors` or `refusals` changed (`refusals` is the error set a caller meets, so a role change that adds `NotAllowed` counts),
    else a patch (budget, `allowed`, steps, move, description). `file` and `identifier` alone are nothing. A thing or a value that changed is a
    patch by itself: what a caller sees shows in the operations' own entries. The largest bump wins, and no difference at all is still a
    patch, because the logbook refuses a version twice, so a rebuilt revision needs a new one. With no production release the next version is
    `1.0.0`. Each change becomes a line of `changes.json`: `{ kind, what, detail?, bump }`, with `what` the operation or, for a part,
    `allowance.spend.budget` (`150ms to 300ms`) or `allowance.spend.payload` (`memo removed, to added`), as the docs show.
63. **Stale is read from main's verdicts, per shipped environment, and printed as `stale <ops> in <envs>`.** For staging and for production
    the latest passing verdict of each operation among those with `ref=refs/heads/main` (`GET /verdicts/latest`, D3 #31), judged against the
    model of the revision it proved: stale when any hash that proof rested on (`Compare.dependsOn`) differs in the working model. A pull
    request's verdict never counts (D3 #8); `test` is never listed; an operation the working model has but the proved one lacked (a new read)
    is unproven, not stale. The line carries the union of operations and of environments (`stale allowance.spend in staging, production`);
    `stale none` when there are none. With a logbook, `architect impact` prints `changes since <release>`, a line per change, `next <version>`,
    `stale`, `proven` (passing in a shipped environment and still holding) and `unproven` (new, or never passed there), and the local
    ledger's finding comes last as `locally stale …`, only when there is one; without a logbook it is exactly Gate 1's output (check 7 of
    layer one is unchanged and passes).
64. **Where the logbook is: `ARCHITECT_LOGBOOK_URL`, else the running `logbook` environment.** The variable wins when set. Otherwise
    `Environments.status({ name: "logbook" })`, which reads the pid and the port that `architect env up logbook` keeps under
    `.architect/environments/logbook/`; this works however L2.02 starts it, so long as it keeps them where every environment does. The
    checks pass no URL (D3 #16: configuration comes from `ARCHITECT_*` variables and the pidfile), so the pidfile is the path they use.
    `version --next` with neither exits 2 and says to run `architect env up logbook` or set the variable; `impact` with neither is local
    only; with a URL that doesn't answer it prints the local lines and a warning on stderr, never a `stale none` it did not check.
65. **`generated/model/changes.json` is written by the commands, never by the generators.** It depends on the logbook, not the blueprint, so
    `nx sync` would make it differ per machine. `architect impact` and `architect generate` write it when a logbook answers
    (`{ from, to, changes, stale, proven }`, `from` null with no release); `Sync` leaves that one path alone instead of deleting it as an
    orphan, so `nx sync:check` stays green whether the file is there or not. When it is committed it records the comparison at that time.
66. **Recording a release: `Releases.record({ logbook, env, model, revision, version })` in `@architect/prove`.** `PUT /models/<revision>`
    with the model as canonical JSON, then `POST /releases { version, revision }`; a version already released is a 409 the caller sees as
    `ReleaseFailed`. L2.05's `promote --to production` calls it with `version` from `Releases.next`. Both writes carry a verified OIDC token,
    taken from `ARCHITECT_LOGBOOK_TOKEN`, else minted from `ARCHITECT_OIDC_ISSUER` and `ARCHITECT_OIDC_CLIENT` (client credentials; the
    local issuer's scenario `ci-main`, which is what the checks set), else GitHub Actions' own token (`ACTIONS_ID_TOKEN_REQUEST_URL`,
    audience `architect-logbook`). L2.02 posts verdicts with the same token; the two should share one minting function when both are on
    `layer/3`.
67. **Models are compared as canonical text.** A model that has been through the logbook has its keys sorted (`canonical`), one just
    compiled does not, and `JSON.stringify` equality saw every declaration as changed (found by the first test against the real logbook:
    `1.0.0` to `2.0.0` for adding a read). `Compare.models` and `Compare.release` now compare `canonical` forms. Hashes were never affected.
68. **`@architect/logbook` is a dev dependency of `prove` and `cli`,** for their tests, which run the real logbook worker and the real issuer
    container. Nothing in them imports it at run time: the commands speak HTTP, so the logbook stays a worker.

## L2.02: test worlds, and the logbook as an environment (16 November 2026, the builder)

Evidence: `design/evidence/L2.02/`. The done-when check is `packages/prove/src/modules/test-worlds/test-worlds.test.ts`
(ports 8970 to 8989); the author's checks 01 and 02 pass against it. These settle what #7 and #14 left open for the
local reading. The GitHub Action itself (`test-pr-<n>`, destroyed in an `always()` step) is the cloud pass's: what it
needs is already here, the job's own token (#54) and the worlds' alarm.

50. **A world in a long-lived environment is a lease on the environment's data, one live world at a time.** The test
    environment's one D1 holds every world's rows, so a world's data is whatever is above a mark. When a world is made
    the worker records, in `_worlds` (made on first use, so no generated migration changes), the highest `rowid` of every
    table, and its expiry; destroying the world deletes every row above those marks (a table made since, such as Better
    Auth's own, counts from 0) in one batch with foreign keys deferred, and marks the lease ended with why (`destroyed`
    or `expired`). A prefix on ids was rejected: ids are made by the runtime and Better Auth, so the marks need no change
    to either. Each world is also its own `World` Durable Object (named by its id, not the shared `world`): it keeps the
    cast, so signed-up people die with the world that signed them up, and it holds the alarm. Every destruction, whether
    the alarm, a reap or an explicit destroy, goes through that one object, so they queue and only the first does the work.
    The routes are `/_world/worlds` (`POST {id, lifetimeMs}`, `GET`, `DELETE /<id>`, `POST /reap`), open only where the
    environment sets `ARCHITECT_WORLDS=1`, which `env up` does for an environment whose blueprint declares a `lifetime`.
    Known limits, for the layer that needs them: a thing that lives as an actor has its own Durable Objects, which a world
    does not delete yet, and the generated server has no R2 binding, so there is no prefix to clear.
51. **One live world at a time, and why that is enough.** The marks are only right if nothing else writes while the world
    lives, so a second `POST` while one lives is a 409 `WorldLive` naming the first (the CLI says to reap), and a world
    past its lifetime is destroyed first, silently, so a dead run never blocks the next. A pull request has its own test
    environment in CI (`test-pr-<n>`), so one at a time costs nothing there; on this Mac it means two proves of one
    project take turns. A lease per world with a tag on every row is the way out when that is not enough; it needs the
    runtime's store and Better Auth to carry the tag, which is why it is not done now.
52. **The test environment has a collector of its own.** The journeys' evals read spans, and prove must not start a
    container of its own for `--env test`: a run killed with SIGKILL would leave it behind, and the check forbids that. So
    an environment that hosts worlds starts its collector in `up` (`Collectors.launch`, a container named for the
    environment's folder, writing `.architect/environments/<env>/telemetry/`), points `OTLP_URL` at it in its config, and
    `down` removes it. Prove reads that folder (`Collectors.read`). This is also what `watch` will read for staging and
    production (#12); they get theirs when L2.08 needs it, so `env up staging` still needs no Docker.
53. **`prove --env test` proves the revision it names.** It builds the bundle if there is none, brings the environment up
    on it (restarting a running one that has another bundle, state kept), makes `test-<id>` (eight hex digits) with the
    environment's lifetime (`ARCHITECT_LIFETIME` overrides it: `20s`, `30 minutes`, `2 hours`), and prints each line as it
    becomes true, so a run killed part-way has already said which world it made. The lifetime prints as given, else the
    environment's own in its largest exact unit (`2h`). A verdict is `pass` for an operation only when every one of its
    evals passed and no journey failed (D2 #80); failing verdicts are posted too. The world is destroyed whether the run
    passes, fails or is interrupted, and `world destroyed` is printed only once that is true; a run whose verdicts the
    logbook refuses (401) still destroys its world, then exits 2 with `prove couldn't run`. The CLI reads
    `ARCHITECT_LOGBOOK_URL` to use a logbook that is not the local one; otherwise it is the running `logbook` environment.
54. **The token is the CI job's own, or the local issuer's, and never printed.** `ARCHITECT_OIDC_ISSUER` wins (client
    `ARCHITECT_OIDC_CLIENT`, default `ci-main`; client credentials against `<issuer>/token`, as the mock server takes
    them); without it, a GitHub Actions job's `ACTIONS_ID_TOKEN_REQUEST_URL` and `_TOKEN` ask for audience
    `architect-logbook`. The token is an Effect `Redacted` from the moment it exists, so no log line, error or `String()`
    can carry it (the test checks the printed lines). Minting happens just before posting, not at the start, because the
    issuer's tokens live ten minutes and a prove can take longer.
55. **`reap` starts what it needs and leaves things as it found them.** `worlds reap` starts the test environment if it
    is down (alarms only fire while a workerd runs, #7), asks it to destroy every world past its lifetime, and stops it
    again if it started it, so reaping leaves nothing running. It counts each expiry once: `reaped <n>` is the worlds that
    ended by expiry since the last reap, whether the alarm fired at start-up or the reap itself did the work, so the next
    reap says `reaped 0`. `env status test` adds `worlds <n>` (only while the environment is up) and prints nothing about
    worlds for an environment that hosts none.
56. **`env up logbook` is the logbook's own worker, and a project can be the logbook's neighbour.** `up logbook` takes its
    policy from `ARCHITECT_OIDC_ISSUER`, `_REPOSITORY`, `_REF` and `_WORKFLOW` (the ref and the workflow may each list
    several, comma-separated, so a pull request's `refs/pull/*/merge` can be allowed beside `refs/heads/main`), finds the
    JWKS from the issuer's discovery document, and runs `Logbook.launch` detached with a pidfile, a port and a state folder
    under `.architect/environments/logbook/`. It has no bundle, so `Status.revision` and `sha256` became optional: an
    environment that runs a bundle has them. `prove` now depends on `@architect/logbook`, so the logbook is one more
    package to publish with the others (`tools/e2e/starter.sh`).

    thing's own field, with its `of`, `key` and `from`, so a role can still follow it. A thing's field takes the mark of the value or the
    field it is made from. Nothing is secret because it is called `password`. Declared secret in acme and the starter (both blueprints, and
    so the preset, which writes the starter): the values `Password` (sign-up's and sign-in's password) and `Secret` (sign-in's `token`,
    api-key's `key`), and sign-in's `session` answer. That answer is marked on the field, not on `Session.fields.id`: the session's id is
    public where it is only an id (`session.show`), and issuing it, beside the bearer token, is what is secret. The model records
    `visibility` on a field only when it is not public (`"secret"`, or `{ private: ["organization.owner"] }` naming the roles as
    `thing.role`), so a project with nothing marked has the model it had.
81. **Span attributes are an allowlist built from `visibility`, and it fails closed.** `handler/internal/attributes.ts` writes
    `payload.<field>` and `answer.<field>` only for a field whose declared visibility is `public`; a field the declaration doesn't name
    (an answer with an extra key) is not written either. A list read's `items` are cut to the thing's public fields and `state` before
    they become one attribute. The journal's entry for a move drops the event's non-public fields (`move.ts`). Fields of an answer or a
    payload were never the only way in, so the evidence was checked too: step spans carry only `step.kind`, the operation span only the
    operation, the principal and the refusal's name and deciding log, and the log that decided a refusal is the handler author's own
    sentence, which the eval below reads. `subjectOf` now matches the thing's own id by place (`of` and `key`), not by object identity,
    because a field marked secret is a copy.
82. **The Collector is the second guard, and prove builds it from the model.** `Collectors.start(dir, { strip })` and `launch({ …, strip })`
    put an `attributes` processor with one `delete` action per key in both the traces and the logs pipeline, before the file exporter.
    `privateKeys(model)` gives, for every non-public field of every operation, `payload.<field>`, `answer.<field>` and the bare
    `<field>` (a log annotated with it), and the non-public fields of things, errors and events by bare name. A name that is public in
    another operation is deleted there too: the guard leans towards deleting, and a declared public field that goes missing fails its
    own answer-shape eval loudly, which is the right way round. `prove` and `env up` (the test environment's own collector) both pass it.
    The runtime's allowlist is the first guard and the only dependable one in the cloud, where there is no Collector in front of it (O1).
83. **The leak check is part of eval 1, answer shape, not a tenth eval and not a `check` rule.** The nine evals are a contract of the
    gate (`9 evals ✔` per operation); the answer eval already reads `answer.*` off the span and the call's body, and runs per operation
    on every call, so each operation that has a secret is checked on every journey that calls it. A static `check` rule cannot see a
    value a handler logs in a sentence, and `check` runs without a world. It reads two ways, since each catches what the other misses:
    by name (no span or log attribute is keyed `payload.<f>`, `answer.<f>` or `<f>` for a non-public `f`), and by value (the password
    sent and the token, key and session answered appear in no span attribute, log body, log attribute or journal entry of the call;
    values under 8 characters are caught by name only, because a shorter one would match by chance). A failure names the field and
    where it showed up and never repeats the value, so a report is safe to paste. Because a secret is no longer on the span, eval 1 reads
    a non-public answer field's shape from what was answered. Planted in `evals.test.ts`: each way to leak fails.
84. **Refusal codes: `[AL-002] Name { field: value }`, fixed by the model.** A code is the thing's prefix and a three-digit number. The
    prefix is the thing's `code` (`Blueprint.thing({ …, code: "AL" })`) or the first two letters of its name; the compiler refuses a
    prefix that is not 2 to 4 capital letters and two things that share one, naming both. Declared errors are numbered 1, 2, 3 in the
    order they are declared in `errors.ts`: a module's exports come out sorted, so `Blueprint.error` stamps each class with a counter
    (`sequence`) and the compiler sorts by it. The machine's own refusal is always 900 (`AL-900`), so adding an error never moves it,
    and the runtime's `NotAllowed` is `AR-001`, a prefix that belongs to no thing. The model records every code (`things[].code`,
    `errors[].code`, `machine.notFrom.code`, and `refusals`, name to code, for the whole project). **It never moves once released:**
    `Compare.release` reads `refusals` and makes a changed or removed code a major change (`refusal:<Name>`, "AL-002 to AL-003"), and
    a new error added at the end moves nothing (the model test adds one and checks the others). Not taken: a numbered pin on each
    error. The order is the declaration, and Compare is what notices an edit that reorders it.
85. **The code is added beside the tag, in the answer, the SDK, the CLI and the docs.** The wire answer is `{ _tag, code, …fields }`. Each
    generated wire class has `code` as a field and as a static, and `Wire.refusals` reads it from the class, so a server built from an older
    `main.ts` still sends it. `Errors.codes` is in the SDK, with `Errors.shown`, each refusal's public fields. The CLI prints
    `[AL-001] AllowanceExceeded { remaining: 300 }` to stderr, with the exit code unchanged, and only public fields; the docs' refusals
    table has a `code` column after the exit (so every line it had is still there) and a field's row says `(secret)` or `(private to organization.owner)`. The declared-errors eval checks
    that every refusal answer carries the code the model fixed. The wire still carries every declared field of an error: no error in
    acme or the starter has a non-public field, and answering a refusal's private field by the caller's role belongs to L2.08, the
    first consumer outside the server. A refusal's span still carries its name and deciding log, not its fields.
86. **`runs` and the test kind, and the step kinds.** `Blueprint.operation({ runs })` is `client`, `server` or `chain`, default `server`.
    The compiler refuses any other with the target that would run it (`target-noir` for the caller's device, `target-solidity` or
    `target-noir` for a chain), and the model says `runs: "server"` on every operation. `StepKind` is open
    (`"database" | "wait" | "sync" | "check" | "prove" | (string & {})`): the three new kinds are named and reserved, and nothing in the
    runtime or the evals matches on all of them. `Blueprint.operation({ test })` is `unit` (the default) or `network`; the model carries it,
    for a target that says a guarantee needs a network test. Nothing reads it yet, because the Effect target has no such guarantee.
