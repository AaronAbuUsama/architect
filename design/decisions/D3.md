# D3: destinations, versions, secrets, and how layer two ships on this Mac

Decided 16 November 2026 by the builder (Aaron gave architectural ownership). Evidence: `design/wayfinding/stage-3.md`
(research R1 to R4, run that day from primary sources at the pinned versions, with live experiments on workerd).

## The build plan's three recommendations stand

1. **Versions come from the model diff.** An added operation or read is minor. A changed payload, answer or error
   set is major. A budget or docs change is a patch. `architect version --next` prints the release version (`1.1.0`).
   Staging publishes prereleases of it (`1.1.0-next.<n>`, dist-tag `next`); production publishes the version itself.
2. **Secrets are named per environment.** `blueprint/environments/<env>.ts` declares secret names only. Locally their
   values are generated into `.architect/environments/<env>/secrets.env` (mode 0600), never on a command line, where
   `ps` would show them. In the cloud pass Alchemy sets them as Cloudflare secrets.
3. **Verdicts live in the logbook.** It is a Durable Object behind one worker, with R2 for each revision's model. On
   this Mac it is a long-lived local environment of its own.

## How shipping runs locally (stage 3)

4. **A local environment is a long-lived workerd, driven by wrangler.** Each of test, staging and production runs
   `wrangler dev` on its own port, with its own `--persist-to` state, config folder and `--inspector-port 0`, and its
   state survives a restart (R1 measured both). `architect env up|down|status` keeps a pidfile and a port per
   environment under `.architect/environments/`, and waits for wrangler's ready line.
5. **Alchemy waits for the cloud pass.** Its local mode is a foreground dev session on its own workerd, not a deploy;
   its `deploy` and `destroy` always need a Cloudflare account; its v2 line is weekly-changing beta (R1). So
   `generated/infra` holds the per-environment wrangler configs now, and gains the Alchemy stack, deploying the same
   bundle, when the cloud pass turns the `cloudflare` destination on. Until then that destination says it is not
   built.
6. **One artefact per revision.** `wrangler deploy --dry-run --outdir` builds `main.js` once, with no credentials;
   two builds of the same source hash the same (R1). The bundle is kept at
   `.architect/artefacts/<revision>/main.js` with its sha256, and every environment runs that file unchanged
   (`no_bundle: true`). The worker reports the hash, so `promote` can show that production runs what staging proved.
7. **Test worlds have a lifetime.** A test world's Durable Object sets an alarm at creation and destroys the world at
   expiry: `deleteAll`, its D1 rows and its R2 prefix. Alarms fire and survive restarts under local workerd, but only
   while a workerd runs (R1), so `architect worlds reap` starts the test environment to let past-due alarms fire. In
   CI each pull request gets `test-pr-<n>`, destroyed in an `always()` step.
8. **Signed verdicts.** The logbook accepts a verdict only with an OIDC token for audience `architect-logbook`,
   verified with `jose` 6.2.15 against the one issuer its environment names, RS256 only, with repository, ref and
   workflow checked. In GitHub CI that is GitHub's own issuer (`token.actions.githubusercontent.com`, the job given
   `id-token: write`). On this Mac it is a real OIDC server, `ghcr.io/navikt/mock-oauth2-server:6.1.4` (digest
   `sha256:647dd8c7…0192`), whose clients are scenarios (`ci-main`, `ci-other-branch`). A forged token, a token from
   another issuer and no token are each a 401 (R2 measured all three on workerd). A deployed environment may name
   only an `https` issuer; the environment check fails the build otherwise. Fork pull requests get no token, so they
   can't post verdicts.
9. **Publishing stays on the machine.** The SDK and CLI publish to Verdaccio, with explicit no-proxy rules for the
   project's own names (the unscoped `acme` exists on npm), always with `--tag next` for a prerelease (pnpm silently
   tags it `latest` otherwise), and installs name the exact version (R3). CLI binaries are Node single executables:
   an esbuild CommonJS bundle injected with `postject` 1.0.0-alpha.6 into the official Node 24.22.2 binary for each
   target (macOS arm64, Linux x64). The Homebrew tap is a local git repository whose formula points at `file://`
   tarballs with their sha256, installed by its full name so Homebrew's tap trust covers just that formula, then
   uninstalled and untapped. GitHub releases are the cloud pass's switch: `gh release create` with the same
   tarballs and `SHA256SUMS`, and the formula's `url` the only difference.
10. **Sign-in in deployed environments is Better Auth's.** The CLI signs in by device code with Better Auth 1.7.15's
    `deviceAuthorization` plugin (client `acme-cli` only, table `auth_device_code`). A test approves as ada without a
    browser: it claims the code with her session, then approves it (R4).
11. **The remote MCP server is one stateless worker route.** `@modelcontextprotocol/sdk` 1.32.2's web-standard
    streamable HTTP transport, a fresh server per request, the Cloudflare JSON-schema validator (workerd forbids
    Ajv's generated code). OAuth 2.1 comes from `@better-auth/oauth-provider` 1.7.15 with the `jwt` plugin, on the
    same D1 as sign-in, so a token's subject is the same principal and the existing role check refuses a call. No
    Durable Object is needed. Cloudflare's `McpAgent` is feature-frozen and keeps tokens in KV (R4).
12. **`watch` reads the local OTLP sink.** The same evals, without journeys and without coverage, run over what the
    Collector recorded from an environment's traffic. Axiom is the cloud pass's sink, behind the same reader.
13. **The portal is a read-only site on workerd,** reading the logbook: the blueprint, the docs, the verdicts per
    environment and what is stale.

## Spikes, before the steps that need them

- `mcp-oauth`: on local workerd, `oauthProvider` with the `jwt` plugin on `AuthD1`. Do its tables create, does JWT
  signing work, is a JWT access token issued for `resource=<mcp url>`, and how does consent go for a signed-in
  session? Then an MCP client completes OAuth headless as ada and calls one tool.
- `single-binary`: a Linux x64 SEA cross-built on this Mac from Node 24.22.2, run on `ubuntu-latest`, and installed
  through a local tap there (with and without `skip_clean`); the macOS arm64 one installed through the tap, its
  signature still valid.
- `ci-oidc`: on a throwaway branch, a job with `id-token: write` mints a token for `architect-logbook`, posts it to a
  workerd logbook on the runner, which verifies it against GitHub's real JWKS. Records the claims on a same-repo pull
  request.
