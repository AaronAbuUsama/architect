## The idea

Every piece of data in an Orthograph system sits in one of four places, and one rule sorts it: **if Orthograph owns
the schema and every write goes through Orthograph's commit, the place is a store. If anything else owns it, it is a
source, reached through an adapter** (K3, "The rule that sorts every case"). A thing **lives** in a store: its `lives`
names one, or says nothing and gets the project's default. A **source** is someone else's data. A **view** is a list
kept from events, ours and a source's, and can always be rebuilt. And **a projection's own state** is data a
projection needs for itself, such as the portal's notes and chat threads: they are things too, in that projection's
own store. Each place has exactly one writer. A store is written only by its commit, a source only by its owner, and a
view only by the events it keeps.

## The smallest example

Tickets keeps two things, an `event` and a `ticket`. Here is where each sits, in the blueprint, in the one handler that
writes them, and in what Orthograph generates:

```text tree=examples/tickets
blueprint/
  things/
    event/  an event with a fixed number of places
      thing.ts
    ticket/  a ticket for some seats, held under a name
      thing.ts
src/
  event/
    claim.ts  the handler that writes both
generated/
  server/
    migrations/
      0001_things.sql  both tables, the journal and the request keys
    wrangler.jsonc  the one D1 binding
```

Neither thing says where it lives, so both live in the project's default store:

```ts file=examples/tickets/blueprint/things/event/thing.ts lines=1-7
import { Blueprint } from "orthograph";
import { Count, Title } from "../../values/counts.ts";

export const Event = Blueprint.thing({
  description: "An event with a fixed number of places, and free tickets for them.",
  fields: { id: Blueprint.id("evt"), title: Title, places: Count, claimed: Count },
});
```

```ts file=examples/tickets/blueprint/things/ticket/thing.ts lines=1-8
import { Blueprint } from "orthograph";
import { Event } from "../event/thing.ts";
import { Count, Holder } from "../../values/counts.ts";

export const Ticket = Blueprint.thing({
  description: "A free ticket for some seats at an event, held under a name.",
  fields: { id: Blueprint.id("tkt"), event: Event.fields.id, holder: Holder, seats: Count },
});
```

On Cloudflare the default store is D1. Orthograph writes its schema from the model, and nobody writes it by hand. This
is the whole file. Each thing is a table, and a row carries its fields, its state and the version every commit is
guarded by. The journal of events and the answers kept under request keys are tables in the same database, because
they are committed with the rows:

```sql file=examples/tickets/generated/server/migrations/0001_things.sql lines=1-34
-- Generated from the blueprint. Do not edit.
-- Stage one rebuilds the local database on every `ortho dev`; migrations between versions arrive in stage three.
CREATE TABLE "event" (
  "id" TEXT PRIMARY KEY,
  "title" TEXT NOT NULL,
  "places" TEXT NOT NULL,
  "claimed" TEXT NOT NULL,
  "state" TEXT,
  "version" INTEGER NOT NULL DEFAULT 0
);
CREATE TABLE "ticket" (
  "id" TEXT PRIMARY KEY,
  "event" TEXT NOT NULL,
  "holder" TEXT NOT NULL,
  "seats" TEXT NOT NULL,
  "state" TEXT,
  "version" INTEGER NOT NULL DEFAULT 0
);
-- Every event a move emitted, with the trace of the call that made it (language-effect's Journal).
CREATE TABLE "_journal" (
  "seq" INTEGER PRIMARY KEY AUTOINCREMENT,
  "trace" TEXT NOT NULL,
  "operation" TEXT NOT NULL,
  "move" TEXT NOT NULL,
  "subject" TEXT NOT NULL,
  "event" TEXT NOT NULL,
  "fields" TEXT NOT NULL
);
CREATE INDEX "_journal_trace" ON "_journal" ("trace");
-- Each idempotent call's answer, under its operation, caller and request key, committed with the call itself.
CREATE TABLE "_requests" (
  "key" TEXT PRIMARY KEY,
  "answer" TEXT NOT NULL
);
```

`WORLD` is not a store. It serves `/_world/*`, the test worlds of `ortho dev` and `ortho prove`, and
`generated/server/main.ts` answers that path only where worlds live. No ticket or event lives in it.

Now the one operation that writes both. `event.claim` writes a ticket and updates its event, and the enforcer commits
them together, with the event it emits and the request key. This is the whole handler, as scaffolded and then edited:

```ts file=examples/tickets/src/event/claim.ts lines=1-31
// Scaffolded from blueprint/things/event/verbs/claim.ts. Yours from now on.
import { Effect } from "effect";
import { Ids, Records } from "@orthograph/language-effect";
import type { Handler } from "../../generated/api/src/event/claim.handler.ts";
import { Event } from "../../blueprint/things/event/thing.ts";
import { SoldOut } from "../../blueprint/things/event/errors.ts";
import { Ticket } from "../../blueprint/things/ticket/thing.ts";

/** Claim a ticket for one or more seats, held under a name. */
const claim: Handler = ({ event, holder, seats }, { steps, move }) =>
  Effect.gen(function* () {
    const records = yield* Records;
    // The machine's check already found the event on sale, so it exists.
    const found = yield* steps.load(records.find(Event, event));
    if (!found) return yield* Effect.die(new Error(`event ${event} was checked and then not found`));
    const places = found["places"] as bigint;
    const claimed = found["claimed"] as bigint;
    const left = places - claimed;
    if (seats > left) {
      yield* Effect.logInfo("more seats asked for than places left").pipe(Effect.annotateLogs({ seats: String(seats), left: String(left) }));
      return yield* new SoldOut({ left });
    }
    // The ticket is written in the same commit as the claim, already issued.
    const ticket = yield* Ids.of(Ticket.fields.id);
    yield* steps.issue(records.insert(Ticket, { id: ticket, event, holder, seats }, "issued"));
    yield* steps.count(records.update(Event, event, { claimed: claimed + seats }));
    yield* move(seats === left ? "soldOut" : "onSale");
    return { ticket, left: left - seats };
  });

export default claim;
```

Lines 25 and 26 write two things, a ticket and an event. Neither writes to the database yet. They are queued, and the
enforcer commits them as one set of writes with the `TicketsClaimed` event and the kept answer
(`packages/language-effect/src/modules/handler/service.ts:71`). If another claim changed the event meanwhile, the version
guard conflicts and the whole call runs again, so a ticket is never written without its count.

That is why the event is not an entity. An entity is one addressed instance that commits on its own, and a call has
one owner. Make the event an entity and the ticket would sit in another store, and this operation would write two
(K3 item 5). The compiler refuses that, and the claim becomes a workflow with a waiting state between two commits.
Both things in one database keep it one call and one commit.

Tickets has one store, so it has no source, no view and no projection with state of its own. Those come with the
workshop, from layer 4.

## How it works

### The four places

| Place | Who owns the schema | Who writes it | How a handler reaches it | Explained on |
|---|---|---|---|---|
| a store | Orthograph, from the model | only the commit: one call's writes, its events and its request key, all or nothing | `Records`, inside a step | [stores](stores.mdx) |
| a source | someone else | its owner, never us | an adapter's typed calls, as steps | [adapters](adapters.mdx) |
| a view | Orthograph | only the events it keeps, ours and a source's | the reads generated for it | [views](views.mdx) |
| a projection's own state | the projection | its own operations, through its own store's commit | it is a store, so as above | [portal](portal.mdx) |

### A thing lives in a store

`lives` is the one place a declaration says where a thing's state is. Today it takes one of two built-in kinds, and
the default is a D1 row:

```ts file=packages/orthograph/src/modules/things/types.ts lines=26-32
  /** Who owns its state: a D1 row with a version column (the default), or a Durable Object per instance (D1 #1). */
  readonly lives: Lives;
  /** The prefix of this thing's refusal codes (`AL` in `[AL-002]`); the compiler takes two letters of its name when unset. */
  readonly code: string | undefined;
}

export type Lives = "database" | "entity";
```

K3 opens that list: a store is declared under `blueprint/stores/`, named by its path, and `lives` takes it. A
one-store app, like tickets, changes nothing:

```ts planned=M1.17 path=blueprint/stores/ledger.ts
// blueprint/stores/ledger.ts: the name is the path, "ledger"
export default Blueprint.store.database();

// blueprint/things/entry/thing.ts
import ledger from "../../stores/ledger.ts";
export default Blueprint.thing({ description: "…", fields: { … }, lives: ledger });
```

The kinds are supplied by hosts and languages ([languages-and-hosts](languages-and-hosts.mdx)): `database` (D1) and
`entity` by the Cloudflare host. An entity is one addressed instance that commits on its own, named after Effect
Cluster's `Entity`; on Cloudflare it is a Durable Object per instance (K8). A chain is a host too, and the store kind that runs
on it is `chain`, supplied by the Solidity language. How a thing that lives on a chain is declared, and what its
commit looks like, waits on K7.

### What crosses the edge of a store

One call commits to one store: the compiler refuses an operation whose steps write to two (K3 item 5). Work that
changes two stores, or a store and a chain, is a [workflow](workflows.mdx), with a waiting state between the two
commits (K5 seam 6). A source is never migrated and never committed to. A handler only calls it, through a step the
operation declares, so the call shows in the trace with its declared errors (K3 item 8).

### A projection's own state

Some projections keep data. The portal keeps notes about declarations and chat threads, and neither is part of the
app the developer is building. Both are things in the portal's own store, declared by the portal feature, so they get
the same commit, migrations and journal as the app's own things. A plugin's store is named by its mount plus the
store's path, so it never collides with the app's (K3 item 7). Nothing of agent-native's database comes with it: the
portal's pieces are ported into our own code, over D1 (K5, "Porting from agent-native").

### Seeing all of it

The data map, `generated/data/map.md`, and the portal's data page list every store with its kind, binding and
migrations, every source with its adapter, calls and stand-in, and every view (K3 item 10, slice M5.06).

## Choices

| You have | Put it in | Because |
|---|---|---|
| state your operations change, and the schema is yours | a store, the default unless it must be apart | only a store's commit keeps writes, events and the request key together |
| one instance that many calls change at once | the `entity` kind | each instance commits on its own, so calls on different instances never race |
| data someone else's system owns, such as a bench of candidates or a contract you didn't write | a source, through an [adapter](adapters.mdx) | Orthograph would otherwise migrate or write a schema it doesn't own |
| a list across stores, or across ours and a source's | a [view](views.mdx) | an entity has no list, and a source can't join a query of ours |
| files | a field, with the bytes in R2 | R2 can't take a commit, so it is never where a thing lives |

## What it is not

- **Not where the detail of a commit is explained.** The version guard, migrations, binding a store per environment
  and kinds in depth are on [stores](stores.mdx), in layer 4.
- **Not a "home".** That word is retired: a thing lives in a store (K3, ledger `G-03`).
- **Not a cache, KV or R2.** None of them can take an atomic commit, so no thing lives in one (K3 item 3).
- **Not how a field is hidden.** Who may see a field is visibility, on [things](things.mdx).

## Notes

<Note kind="decision" decision="K3">A place is a store when Orthograph owns its schema and every write goes through
its commit. Anything else is a source, reached through an adapter. The word "home" is retired (ledger `G-03`).</Note>

<Note kind="decision" decision="K5">A chain is a host, and its store kind is `chain`. A server call that sends a
transaction writes two stores, so it is a workflow. Everything else about chain data (how a thing is declared on one,
what its commit returns to a caller, where private state fits, ledger `G-04`, `STO-02` and `X-18`) waits on K7.</Note>

<Note kind="question" id="kind-capabilities" slice="M1.17">A store kind is to declare what it can serve (lists,
search, private state), so the compiler can refuse a read it can't serve. No shape for that declaration exists yet
(ledger `STO-07`).</Note>
