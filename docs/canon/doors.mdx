## The idea

Every operation is **enforced in exactly one place**. For an Effect operation, that place is the wrapper on the Worker,
which runs the role check, the machine's check, the handler, the answer check and the commit, in a fixed order. For a
chain operation, it is the contract. That place is the operation's **enforcer**, and the operation it serves is the
**served operation**. A **door** is a way in: the HTTP API, the SDK, the CLI, an MCP tool, or an **action** that a
screen or an agent binds to. Every door is made from the operation's declaration, and every door reaches the same
enforcer. So the rule is: **a door never decides anything.** It carries a payload, a caller and a **request key** in,
and an answer, a refusal with its code, or a defect out. The **SDK contract** is how the other doors do that: the
caller is set once on the client, one request key holds across retries, and every declared refusal is a typed error.

## The smallest example

`event.claim` is declared once, and every door below is made from that declaration. Here is where each file sits:

```text tree=examples/tickets
src/
  event/
    claim.ts  the handler you write
generated/
```

The declaration is the only file a door reads. It says what goes in, what comes out, what may be refused and who may
call:

```ts file=examples/tickets/blueprint/things/event/verbs/claim.ts lines=1-18
import { Blueprint } from "orthograph";
import { Event } from "../thing.ts";
import { machine } from "../machine.ts";
import { SoldOut } from "../errors.ts";
import { Ticket } from "../../ticket/thing.ts";
import { Count } from "../../../values/counts.ts";

export default Blueprint.operation(Event, {
  description: "Claim a ticket for one or more seats, held under a name.",
  payload: { event: Event.fields.id, holder: Ticket.fields.holder, seats: Count },
  answer: { ticket: Ticket.fields.id, left: Count },
  move: machine.moves.claim,
  errors: [SoldOut],
  allowed: [Blueprint.anyone],
  steps: { load: Blueprint.step.database(), issue: Blueprint.step.database(), count: Blueprint.step.database() },
  idempotent: "request", // sent twice with one request, it issues one ticket
  budget: { p95: "150 millis" },
});
```

**The SDK door** is one function, built on the endpoint's client:

**The CLI door** is a command built on the SDK function. Its flags are the payload's fields, and the declaration
decodes them:


Then the HTTP door: the caller is read from `authorization`, the request key from `idempotency-key`, and the route
calls the same served operation.

```ts file=examples/tickets/generated/server/main.ts lines=46-62
/** Who is calling, then the operation or read, its refusals sent as their wire classes. */
type Run = (payload: never, principal: Principal, request?: string) => Effect.Effect<unknown, unknown, unknown>;
const call = <P>(served: { readonly run: Run }, payload: P, headers: Readonly<Record<string, string | undefined>>) =>
  Effect.flatMap(Principals, (principals) => principals.of(headers["authorization"])).pipe(
    // The caller's idempotency key: for an operation declared `idempotent: "request"`, the same key is one call.
    Effect.flatMap((principal: Principal) => served.run(payload as never, principal, headers["idempotency-key"])),
    refusals,
  ) as Effect.Effect<never, never, Services>;

const EventLive = HttpApiBuilder.group(Api, "event", Effect.fn(function* (handlers) {
  // The services are taken once, when the routes are built; each request keeps its own tracer and span.
  const services = Context.pick(SqlClient.SqlClient, Store, Busy, Principals, Journal, Auth)(yield* Effect.context<Services>());
  return handlers
      .handle("claim", ({ payload, request }) => call(eventClaimServed, payload, request.headers).pipe(Effect.provideContext(services)))
      .handle("close", ({ payload, request }) => call(eventCloseServed, payload, request.headers).pipe(Effect.provideContext(services)))
      .handle("get", ({ payload, request }) => call(eventGetServed, payload, request.headers).pipe(Effect.provideContext(services)))
      .handle("open", ({ payload, request }) => call(eventOpenServed, payload, request.headers).pipe(Effect.provideContext(services)));
```

And the MCP door: one tool per operation, calling the very same served operations.

```ts file=examples/tickets/generated/server/main.ts lines=121-126

const tools = Mcp.tools<Services>({
  catalog,
  served: { "event.claim": eventClaimServed, "event.close": eventCloseServed, "event.get": eventGetServed, "event.open": eventOpenServed, "ticket.cancel": ticketCancelServed, "ticket.check-in": ticketCheckInServed, "ticket.get": ticketGetServed },

```

Nothing above was written by hand. `SoldOut` reaches every door with its code because the enforcer refused it, not
because the door checked.

## How it works

### The enforcer, in order

The wrapper runs every call to an Effect operation through the same order (`packages/language-effect/src/modules/handler/service.ts`):

1. **decode** the payload against the declaration, or refuse `InvalidPayload` (`service.ts:104`);
2. **role**: may this caller call? (`service.ts:46`);
3. **span**: the operation's own span opens only once the caller may call (`service.ts:83`);
4. **replay**: a request key already answered gets the kept answer, and nothing changes (`service.ts:52`);
5. **machine**: is the thing in a state this move starts from? (`service.ts:57`);
6. **handler** and its steps, counted (`service.ts:60`);
7. **answer check**: an answer outside its declaration is the handler's bug, and dies (`service.ts:64`);
8. **commit**: the writes, the move's events and the kept answer, all or nothing (`service.ts:71`).

The last four, as code:

```ts file=packages/language-effect/src/modules/handler/service.ts lines=57-73
        yield* checkFrom(op, notFrom, payload, unit);
        const chosen = yield* Ref.make<string | undefined>(undefined);
        const move = (to?: string) => chooseOutcome(name, op, to).pipe(Effect.flatMap((o) => Ref.set(chosen, o)));
        const answer = yield* busy.counted(handler(payload, { principal, steps, move })).pipe(withRecords, logs.around);
        // Recorded before the check, so an answer outside its declaration is evidence `prove` can name.
        yield* Effect.annotateCurrentSpan(answerAttributes(answer, op.answer));
        // An answer that breaks its declaration is the handler's bug, never the caller's: it dies, loudly.
        const wire = yield* check(answer).pipe(
          Effect.mapError((e) => new Error(`${name} answered outside its declaration: ${e.message}`)),
          Effect.orDie,
        );
        const outcome = yield* Ref.get(chosen);
        const entries = outcome === undefined ? [] : [yield* applyMove(name, op, payload, answer, outcome, unit)];
        const request = key === undefined ? {} : { request: { key, answer: JSON.stringify(wire) } };
        const committed = yield* store.commit({ writes: yield* unit.writes, entries, ...request });
        if (committed === "conflict") return yield* new Conflict();
        return answer;
```

A `conflict` reruns the whole attempt, up to 64 times (`service.ts:21`). For a chain operation the enforcer is the
contract, with the machine, roles and refusals compiled into it. How an operation maps to a contract function, and
which functions a client may reach, waits on K7.

### The doors

Each door kind exists once per operation (K5 seam 5):

| Door | You write | Falls out | Enforced by | Its evidence |
|---|---|---|---|---|
| HTTP API and OpenAPI | nothing | from the model | the wrapper, on the Worker | the request's span as the parent |
| SDK | nothing | from the model, per language | the operation's enforcer | the caller's span and the request key |
| CLI | nothing | built on the SDK | the same | the process span, and the exit code against the error's code |
| MCP tools | nothing | one tool per operation the rule admits, on the Worker | the same | the tool span |
| actions | where they bind | from the model, built on the SDK | the same | the action's span as the parent |

Which operations become an MCP tool or an agent tool follows `allowed` and `via` (K2's inclusion rule): an operation
that is `.notVia(Via.agent)` is never one ([roles](roles.mdx)).

### The SDK contract

Today the caller's token is set once, on the client's layer, and an SDK function takes only a payload. The Worker
already keeps an answer under a request key, read from the `idempotency-key` header
(`examples/tickets/generated/server/main.ts:51`), but no generated client sends one yet. M1.12 makes the SDK the
contract every other door builds on:

```ts planned=M1.12 path=examples/tickets/caller.ts
// the caller is the client's, not the call's
const client = Tickets.layer({ url, credential: Credential.session(cookie) });

// typed refusals in the error channel; one request key across retries
const claimed = yield* Sdk.event.claim({ event, holder: "Amina", seats: 2n }, { requestKey });
//    Effect<{ ticket, left }, SoldOut | EventNotOnSale | InvalidPayload, Tickets>
```

- **The caller** is set once, on the client's layer: a session, a key, the device flow or an agent's OAuth token.
  Never per call.
- **The request key** is the caller's, or the SDK makes one when the call starts and keeps it across its own retries.
  A screen makes one when its form opens, and an agent tool uses its tool call's id. For an operation declared
  `idempotent: "request"`, the same key from the same caller is one call ([operations](operations.mdx)).
- **Typed refusals**: every declared error is a class in the error channel, with its refusal code. A defect is a die.

A chain operation's SDK call returns a submission, with its confirmation later, once K7 has settled how a chain call
reaches its contract.

### Actions

An action is one more door: generated from an operation, for a screen or an agent tool to bind to, and built on the
SDK. It keeps agent-native's `defineAction` field names, so agent-native's templates, docs and skills read naturally
against it. That is all the compatibility there is: the shape is ported into our own `actions` module, in Effect, and
nothing of agent-native runs or is installed (K5, "Porting from agent-native"). For `event.claim`, each field comes from
a part of the declaration:

```ts planned=M1.22 path=examples/tickets/generated/actions/event/claim.ts
// Generated from blueprint/things/event/verbs/claim.ts. Do not edit.
import { defineAction } from "orthograph/actions";   // our port of the shape, M1.23

export default defineAction({
  description: declaration.description,             // "Claim a ticket for one or more seats, held under a name."
  schema: standard(declaration.payloadSchema),      // the payload: event, holder, seats
  outputSchema: standard(declaration.answerSchema), // the answer: ticket, left
  errors: refusalsOf(declaration),                  // SoldOut, EventNotOnSale, with their codes
  readOnly: false,                                  // true only for a read, such as event.get
  retrySafe: true,                                  // idempotent: "request", and the SDK keeps one key
  needsApproval: false,                             // nothing to sign; a chain write would be true
  agentTool: true,                                  // false when the operation is .notVia(Via.agent)
  mcpTool: false,                                   // MCP is the Worker's own door, once per operation
  run: (args, ctx) => ctx.sdk(Sdk.event.claim(args, { requestKey: ctx.callId })),
});
```

**An action holds no authority.** Its `run` is the SDK, so the enforcer decides every time. `agentTool` and `mcpTool`
decide what a screen or a tool is offered, never what is allowed. `mcpTool` is `false` because MCP already has its
door, on the Worker; a second MCP tool for the same operation would be a second door of the same kind.

## Choices

| You want | Use | Because |
|---|---|---|
| to call an operation from your own TypeScript | the SDK | typed refusals and one request key, and it is remade when the blueprint changes |
| to call it from a shell or a script | the CLI | it is the SDK, with the refusal's exit code |
| an agent elsewhere to call it | the MCP tool | it is on the Worker, signed in with the person's own token |
| a screen or your app's agent to call it | the action | it binds to a screen or an agent tool and calls through the SDK |
| a client in another language | the SDK for that language | every SDK keeps the same contract |

A hand-written client is never a door. It drifts the day an operation changes, and it leaves different evidence from
the doors a journey checks ([projections](projections.mdx), the replay rule).

## What it is not

- **Not where an operation is declared.** What an operation says is on [operations](operations.mdx); what the handler
  does is on [handlers](handlers.mdx).
- **Not where doors are made.** How each output is generated and mounted as a plugin is on
  [projections](projections.mdx).
- **Not the portal.** The portal's "Try it" calls through the SDK as the builder; it is not a door of its own
  ([portal](portal.mdx)).
- **Not an agent-native app.** Actions keep agent-native's field names so an agent-native app could use them, but
  Orthograph is not one, and doesn't run any of it.

## Notes

<Note kind="decision" decision="K5">Each operation has one enforcer, and every door reaches it. An action sits beside
the other doors as one more door; it doesn't replace the MCP tool or the CLI. Each door kind exists once per
operation, so a generated action sets `mcpTool: false`. This answers ledger `PRJ-43`, and `X-05`: MCP is a door of
the one Worker.</Note>

<Note kind="decision" decision="K5">Nothing of agent-native runs. Its action shape is ported into our own Effect code
(M1.23), compatible by field names only, and a change it makes reaches us only when we port it again.</Note>

<Note kind="status" slice="M1.12">Today no generated client sends a request key, so a retry through the SDK or the
CLI is a second call. The Worker already honours the `idempotency-key` header when one is sent. Ledger: PRJ-45.</Note>

<Note kind="status">Chain operations wait on K7. Q4 (how a declared operation maps to a contract's ABI, and which
functions clients may reach) is confirmed or changed there, so this page says nothing more about a contract as an
enforcer.</Note>
