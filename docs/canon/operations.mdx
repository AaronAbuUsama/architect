## The idea

An operation is a verb on a thing: something a caller asks the system to do. It lives in one file,
`blueprint/things/<thing>/verbs/<verb>.ts`, and its name comes from that path, so `spend` on the allowance is
`allowance.spend`. The file declares everything about the call except how the work is done: what comes in (the
payload), what goes out (the answer), the move it makes, how it may say no (its errors), who may call, the named
parts of its work (its steps), whether a retry is safe, and how fast it should be. Every door is made from that one
declaration: the HTTP endpoint, the SDK, the CLI command, the MCP tool and the docs page. One rule decides it: **if a
caller can see it, the declaration says it.** The handler only fills in the work, and the frame it fits is made from
this file. An operation that changes nothing is a read: it has no handler and no move, and answers straight from the
thing's records.

## The smallest example

This is acme's `spend`. Each line is one part of the declaration:

```ts file=examples/acme/blueprint/things/allowance/verbs/spend.ts lines=8-18
export default Blueprint.operation(Allowance, {
  description: "Spend from what is left of this month's allowance.",
  payload: { allowance: Allowance.fields.id, amount: Amount, memo: Memo },
  answer: { remaining: Amount },
  move: machine.moves.spend,
  errors: [AllowanceExceeded],
  allowed: [grantee],
  steps: { load: Blueprint.step.database(), record: Blueprint.step.database() },
  idempotent: "request", // retried with the same request key, it spends once
  budget: { p95: "150 millis" },
});
```

This is what the compiler made of it. Rendered from acme's compiled model:

And this is a read, the smallest kind of operation. It names the fields it answers and who may ask:

```ts file=examples/acme/blueprint/things/allowance/verbs/get.ts lines=6-12
// A read. It changes nothing, so it has no move and no handler: it answers from the allowance's records.
export default Blueprint.read(Allowance, {
  by: "id",
  fields: ["organization", "member", "limit", "spent", "state"],
  allowed: [grantee, owner.of("organization")],
  budget: { p95: "50 millis" },
});
```

## How it works

### What each part is for

| Part | What it says | Who reads it |
|---|---|---|
| `description` | one sentence on what the call does | the docs page, the CLI's help, the MCP tool, the handler's scaffold |
| `payload` | the fields that come in, each a named value or a thing's field | every door decodes against it before anything runs |
| `answer` | the fields that go out | the handler's frame, and the check after the handler answers |
| `move` | the machine move it makes, if any | the machine's check before the handler, and the event after it (see `machines`) |
| `errors` | the refusals that depend on data | the handler's frame, the endpoint, the exit codes |
| `allowed` | the roles that may call | the role check, before the operation's span opens (see `roles`) |
| `steps` | the named parts of the work | the handler, as `steps.<key>(…)`; one span each (see `traces`) |
| `idempotent` | whether the same request twice is one call | the server, which keeps the answer by request key |
| `budget` | how fast it should answer, at p95 | `prove`'s performance eval, and `forman watch` |

Two more parts have defaults you rarely change. `runs` says where it runs and is only `server` today, and `test` says
how its guarantees are tested, `unit` by default
(`packages/forman/src/modules/operations/types.ts:49`).

### The payload and the answer

The payload and the answer are lists of fields, and each field is a named value, never a bare type. `amount` is an
`Amount`, the same value the allowance's `limit` is, so a page, a CLI flag and a Solidity type all agree on what it
means (see `things`). A field that names another thing, like `allowance: Allowance.fields.id`, is how an operation
says which instance it acts on. The role check and the machine's check both find the instance through it.

A payload that doesn't fit is refused before the role check, before the handler, before any span. An answer that
doesn't fit its declaration is never sent: it is the handler's bug, so the call dies (see `handlers`).

### Refusals

A refusal is an answer the operation was built to give: the caller asked, and the system said no, on purpose. Every
refusal has a name, a code and an exit code. Every door shows the name and the code, and the CLI exits with the exit
code. There are three places a refusal can come from.

**Declared errors** depend on the data, and only the handler can know them. They live in the thing's `errors.ts`, each
with the fields it carries and its exit code:

```ts file=examples/acme/blueprint/things/allowance/errors.ts lines=4-7
// Refusals that depend on data. The machine's own refusal, AllowanceNotActive, is generated and never written here.
export class AllowanceExceeded extends Blueprint.error({ remaining: Amount }, { exit: 41 }) {}
export class AllowanceNotFound extends Blueprint.error({}, { exit: 43 }) {}
export class AllowanceLimitTooHigh extends Blueprint.error({ cap: Amount }, { exit: 44 }) {}
```

An operation lists the ones it may give in `errors`. A handler that fails with one it doesn't list doesn't compile.

**The machine's refusal** is made for you. A move from a state it can't start from is refused as
`<Thing>Not<State>`, here `AllowanceNotActive`, carrying the state it was in. The machine declares only its exit code
(see `machines`). It is checked before the handler runs:

<Scenario journey="examples/acme/journeys/revoke-then-spend.ts" step="olga can't spend" />

**The runtime's refusals** belong to no thing. `NotAllowed` is a caller the operation's roles refuse. A read gives
the same `NotAllowed` for an id that doesn't exist, so a read never tells an outsider what exists.

**Codes.** The compiler numbers every refusal, and the model records the number, so no generator works one out:

```ts file=packages/compiler/src/modules/model/internal/codes.ts lines=7-11
/** The refusal of a machine's move that starts from the wrong state. */
export const MACHINE_NUMBER = 900;

/** Refusals the runtime makes for every thing: who may call, before any handler runs. */
export const RUNTIME_CODES = { NotAllowed: "AR-001" } as const;
```

A code is the thing's prefix and a number. Declared errors are 1, 2, 3 in the order `errors.ts` declares them, the
machine's is always 900, and the runtime's take `AR`. So acme's refusals are `AL-001` for `AllowanceExceeded`,
`AL-900` for `AllowanceNotActive` and `AR-001` for `NotAllowed`. The generated CLI exits with each one's exit code:

```ts file=examples/acme/generated/api/src/errors.ts lines=24-34
export const exits = {
  AllowanceExceeded: 41,
  AllowanceNotFound: 43,
  AllowanceLimitTooHigh: 44,
  PersonEmailTaken: 11,
  SessionCredentialsWrong: 10,
  AllowanceNotActive: 40,
  InvitationNotPending: 40,
  OrganizationNotActive: 20,
  NotAllowed: 3,
} as const;
```

A refusal is not a failure. The call worked, and the span ends OK (see `traces`, which owns the difference between a
refusal and a defect in a trace).

### Steps

A step is a named part of the handler's work. The operation declares them, and the handler runs its work through
them: `steps.load(…)` and `steps.record(…)`. Each step is one span named `<thing>.<verb>.<key>`, so
`allowance.spend.load`, and journeys can say a step ran or didn't. In the refusal above, `allowance.spend.record` is
absent, and that is how the journey proves nothing was written.

A step's kind says what does the work. `database` is the store's, `wait` is a timer's. The kinds are an open list:
`sync`, `check` and `prove` are named for languages that run on a chain or a client (N1), and nothing matches on all
of them (`packages/forman/src/modules/operations/types.ts:19`).

### `idempotent: "request"`

A client that retries after a timeout doesn't know if the first call landed. `idempotent: "request"` promises this:
**the same request key, from the same caller, to the same operation, is one call.** The second time, the server
answers what it answered the first time and changes nothing. No step runs, no event is written, and the span says
`request.replayed`:

```ts file=packages/language-effect/src/modules/handler/service.ts lines=51-56
// The same request key from the same caller is one call: answer what was answered, and change nothing.
const kept = key === undefined ? undefined : yield* store.answered(key);
if (kept !== undefined) {
  yield* Effect.annotateCurrentSpan({ "request.replayed": true });
  return yield* decodeAnswer(JSON.parse(kept)).pipe(Effect.orDie);
}
```

The key is the operation, the caller and the request together, so one caller's key never answers another's call:

```ts file=packages/language-effect/src/modules/handler/service.ts lines=88-90
// Keyed by operation and caller as well, so one caller's key never answers another's call.
const who = principal.kind === "person" ? principal.person : "anonymous";
const key = op.idempotent === "request" && request !== undefined ? `${name}|${who}|${request}` : undefined;
```

The answer is kept in the same commit as the work, so a call either landed with its answer kept, or neither happened.
Over HTTP the key is the `idempotency-key` header. The replay comes after the role check, so a stranger who guesses a
key still gets `NotAllowed`.

<Scenario journey="examples/acme/journeys/spend-twice-with-one-request.ts" step="the same request again gives the same answer and spends nothing" />

Without a key, or without `idempotent`, every call is its own call.

### The budget

A budget is how fast the operation should answer, as a p95. It is a target for review, never a failure:

```ts file=packages/forman/src/modules/operations/types.ts lines=28-31
export interface Budget {
  /** A target for review, never a failure. */
  readonly p95: Duration.Input;
}
```

`prove` times every call's span against it, and a p95 over one and a half times the budget is a review note
(`packages/prove/src/modules/evals/internal/run.ts:17`). In a running environment, `forman watch` writes a task for an
operation over its budget, and removes it when the operation is back under. Loosening a budget is a decision, so it
makes the operation's verdicts stale (see `proof`).

### Reads

A read has no handler and no move. It names the thing, how it finds instances (`by: "id"`, or `by: "list"` with the
fields a caller may filter by), the fields it answers, who may read, and a budget. Its answer comes straight from the
thing's records, with `state` as text. A list answers a page, `items` and `next`, and `next` goes back as the
`cursor` for the page after it.

## Choices

### An operation or a read

| | `Blueprint.operation` | `Blueprint.read` |
|---|---|---|
| Changes anything | yes, through its handler and its move | never |
| Has a handler | yes, written by you | no |
| Refuses | its declared errors, the machine's, `NotAllowed` | `NotAllowed` only, for a missing id as well |
| Pick it when | the call changes a thing, or its answer needs work | the answer is fields the thing already holds |

If the answer is fields the thing holds, make it a read. A read you didn't have to write can't have a bug in it.

### A declared error or the machine's refusal

If the answer depends only on the instance's state, let the machine refuse: you write nothing, and it is checked
before the handler runs. Declare an error only when it depends on data the handler reads, like an amount against
what is left.

### Idempotent or not

Declare `idempotent: "request"` on any operation a client might retry that would do harm twice: spending, granting,
sending. It costs one kept answer per key. Leave it off when a second call is harmless, or meant.

## What it is not

- **Not the handler.** The operation says what the call is; the handler does the work, in the frame the operation
  makes. See `handlers`.
- **Not the move.** A move is a machine's step from one state to another, with its event. An operation names the
  move it makes; the machine owns it. See `machines`.
- **Not the role.** `allowed` names roles; what a role is and how it is checked is on `roles`.
- **Not a span.** A step makes a span, but the span, its attributes and how a refusal looks in a trace are on
  `traces`.
- **Not the commit.** An operation's writes land in one commit at the end. What that is, and where, is on `stores`.
- **Not a journey step.** A journey calls an operation, step by step, to prove it. See `journeys`.

## Notes

<Note kind="decision" decision="O2">
  Every call is counted, a bad payload and a stranger included, as `forman.calls` with an `outcome` and a `refusal`
  tag (M1.20). That needs a bad payload to have one name.
</Note>

<Note kind="question" id="bad-payload-name" slice="M1.20">
  A bad payload has no single name. `call` refuses it as `InvalidPayload`
  (`packages/language-effect/src/modules/handler/types.ts:10`), but a read refuses it as `Schema.SchemaError`
  (`types.ts:73`), the server decodes it itself before `run`, and the generated CLI exits 2 for `SchemaError` and 1
  for anything else (`examples/acme/generated/cli/src/output.ts:14`). It has no code and no exit code in the model,
  unlike `NotAllowed`. Should it be a runtime refusal, `AR-002`, with an exit code, the same at every door?
</Note>

<Note kind="question" id="anonymous-request-keys">
  A request key is kept per person. Every caller that isn't a person is keyed as `anonymous` (`service.ts:89`), so
  two different systems or agents sending the same key to the same operation get one answer between them. Should the
  key use the principal's own id for every kind? This matters once agents and system callers land (M2).
</Note>

<Note kind="question" id="code-examples-drift">
  The comment that explains codes gives `[AL-002] AllowanceExceeded { limit: 500 }`
  (`packages/compiler/src/modules/model/internal/codes.ts:1`), and every generated `errors.ts` repeats `[AL-002]`
  (`packages/generators/src/modules/render/internal/api.ts:55`). In acme, `AllowanceExceeded` is `AL-001` and carries
  `remaining`, not `limit`. The design docs also show `Blueprint.error("AllowanceExceeded", …)` with a name string
  (`design/docs/index.html:373`); the code takes no name, because names come from paths and identifiers. Both should
  match the code.
</Note>

<Note kind="question" id="target-means-language">
  The word "target" still means a language in the operation's own types: the step kinds are "reserved for targets
  that run on a chain or a client", and `runs` is only `server` "until a target supports another"
  (`packages/forman/src/modules/operations/types.ts:15`, `types.ts:21`, `types.ts:49`). The tests say the same
  (`packages/forman/src/modules/operations/operations.test.ts:60`, `operations.test.ts:72`). A message users see
  prints it too: "it needs a target …" (`packages/compiler/src/modules/model/internal/describe.ts:169`). And every
  generated `errors.ts` says codes are "stable across targets" (`api.ts:55`). No slice owns the rename to language.
</Note>
