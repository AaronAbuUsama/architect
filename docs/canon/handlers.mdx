## The idea

A handler is the work inside one operation, and it is the only code in an Orthograph project written freehand.
Everything around it is made from the declaration: the decoding, the role check, the machine's check, the spans, the
commit, and every door. The handler gets the decoded payload and a context, and gives back the declared answer or a
declared error. The shape it must fit is its **frame**, a type generated from the operation, so a handler that returns
the wrong thing doesn't compile. The file it lives in starts as a **scaffold**, written once, and is yours from then
on. One rule decides which files you touch: **a file that says "Generated from" is never edited; a file that says
"Scaffolded from" is yours.** A **blank** is a part not written yet, in a declaration or in a handler. It compiles,
and `ortho check` names it, so a project can be honest about what is left.

## The smallest example

A handler is one file per operation. Here is where the pieces of `event.claim` sit, from the declaration to the
handler:

```text tree=examples/tickets
blueprint/
  things/
    event/
      verbs/
        claim.ts  the declaration: what the call is
src/
  event/
    claim.ts  the handler: the only file written freehand
generated/
  api/
    src/
      event/
        claim.handler.ts  the frame the handler must fit
```

`ortho generate` makes two files for `claim`. The frame is the whole of one, and is regenerated every time:

```ts file=examples/tickets/generated/api/src/event/claim.handler.ts lines=1-7
// Generated from the blueprint. Do not edit.
// What the handler is given: its payload and steps; what it may return: its answer or a declared error.
import type { SqlClient } from "effect/sql";
import type { Auth, Handler as Of, Records } from "@orthograph/language-effect";
import type declaration from "../../../../blueprint/things/event/verbs/claim.ts";

export type Handler<R = Records | SqlClient.SqlClient | Auth> = Of<typeof declaration, R>;
```

The frame imports the declaration, and turns it into a type. The other file is the handler, `examples/tickets/src/event/claim.ts`,
scaffolded once and then written. This is the whole file, and all the freehand code the operation has:

```ts file=examples/tickets/src/event/claim.ts lines=1-31
// Scaffolded from blueprint/things/event/verbs/claim.ts. Yours from now on.
import { Effect } from "effect";
import { Ids, Records } from "@orthograph/language-effect";
import type { Handler } from "../../generated/api/src/event/claim.handler.ts";
import { Event } from "../../blueprint/things/event/thing.ts";
import { SoldOut } from "../../blueprint/things/event/errors.ts";
import { Ticket } from "../../blueprint/things/ticket/thing.ts";

/** Claim a ticket for one or more seats, held under a name. */
const claim: Handler = ({ event, holder, seats }, { steps, move }) =>
  Effect.gen(function* () {
    const records = yield* Records;
    // The machine's check already found the event on sale, so it exists.
    const found = yield* steps.load(records.find(Event, event));
    if (!found) return yield* Effect.die(new Error(`event ${event} was checked and then not found`));
    const places = found["places"] as bigint;
    const claimed = found["claimed"] as bigint;
    const left = places - claimed;
    if (seats > left) {
      yield* Effect.logInfo("more seats asked for than places left").pipe(Effect.annotateLogs({ seats: String(seats), left: String(left) }));
      return yield* new SoldOut({ left });
    }
    // The ticket is written in the same commit as the claim, already issued.
    const ticket = yield* Ids.of(Ticket.fields.id);
    yield* steps.issue(records.insert(Ticket, { id: ticket, event, holder, seats }, "issued"));
    yield* steps.count(records.update(Event, event, { claimed: claimed + seats }));
    yield* move(seats === left ? "soldOut" : "onSale");
    return { ticket, left: left - seats };
  });

export default claim;
```

The first line says whose file it is. The imports tie it to the rest: the frame's `Handler` type, the services it runs
on (`Records`, `Ids`), and the blueprint's own `Event`, `SoldOut` and `Ticket`, so a field, a refusal and the second
thing it writes are named by their exports, never by a string. Four kinds of line carry the declaration: the declared
steps (`steps.load`, `steps.issue`, `steps.count`), the declared refusal (`SoldOut`), the second thing's insert, in the
state `"issued"` (see [machines](machines.mdx)), and the move's outcome (`"soldOut"` or `"onSale"`). The rest is
arithmetic on the record.

## How it works

### What a handler gets, and what it returns

The frame is one type, made from the operation:

```ts file=packages/language-effect/src/modules/handler/types.ts lines=29-30
/** What a project writes in `<verb>.handler.ts`: the declared payload in, the declared answer or a declared error out. */
export type Handler<O, R = never> = (payload: PayloadOf<O>, context: HandlerContext<O>) => Effect.Effect<AnswerOf<O>, ErrorOf<O>, R>;
```

- **The payload**, already decoded against the declaration. `seats` is a `bigint` here, never a string.
- **The context**: the caller as a `principal`, one runner per declared step, and `move`:

  ```ts file=packages/language-effect/src/modules/handler/types.ts lines=17-25
  export interface HandlerContext<O> {
    readonly principal: Principal;
    readonly steps: StepRunners<StepsOf<O>>;
    /**
     * Make the operation's move, ending in `to` (or its only outcome). Applied once the handler answers: the instance's
     * state is set and the move's event journalled. A handler that never calls it makes no move and emits nothing.
     */
    readonly move: (to?: MoveTo<O>) => Effect.Effect<void>;
  }
  ```

- **Services**, from the frame's `R`: `Records` to find and change the thing's records, and `Auth`.

It returns an Effect of the declared answer, failing only with a declared error. Both are checked twice. The compiler
refuses a handler that fails with an error its operation doesn't list
(`packages/generators/src/modules/render/handler-type.test.ts:40`). At run time, an answer outside its declaration
is never sent. It dies as the handler's bug:

```ts file=packages/language-effect/src/modules/handler/service.ts lines=63-67
// An answer that breaks its declaration is the handler's bug, never the caller's: it dies, loudly.
const wire = yield* check(answer).pipe(
  Effect.mapError((e) => new Error(`${name} answered outside its declaration: ${e.message}`)),
  Effect.orDie,
);
```

### What runs around it

The wrapper runs in a fixed order (K5, seam 3), all in
`packages/language-effect/src/modules/handler/service.ts`:

1. decode the payload (`service.ts:104`);
2. check the caller's role (`service.ts:46`);
3. open the operation's span (`service.ts:83`);
4. answer a repeated request key, and stop (`service.ts:52`);
5. check the machine can make the move (`service.ts:57`);
6. run the handler and its steps, as counted work (`service.ts:60`);
7. check the answer (`service.ts:64`);
8. commit the writes, the move and its event together (`service.ts:71`).

<Scene name="handler-lifecycle" caption="Drawn with acme's spend; claim runs in the same order. Watch how much happens before the handler starts, and that its writes land only in the commit at the end." />

So a handler never refuses `NotAllowed` or `EventNotOnSale` itself, and never checks the payload's shape. That is why
`claim` can say the event was "checked and then not found": not finding it is a defect, not a refusal.

A handler that dies after writing leaves nothing behind
(`packages/language-effect/src/modules/handler/handler.test.ts:267`). A handler's writes go through `Records`, never
straight to a store, so they land in that one commit (see `stores`). If the commit loses a race with another call,
the whole attempt runs again, handler and all, so a handler must not do anything outside its steps that can't be done
twice (see `operations`).

Three habits the frame can't enforce, which `ortho brief` asks for:

- **Run work through its step.** `steps.load(records.find(…))`, so each part of the work is its own span, and a
  journey can say it ran (see `traces`).
- **Choose the outcome, don't set the state.** `move("soldOut")` picks one of the move's declared outcomes; the runtime
  sets the state and writes the event. An outcome the move doesn't declare dies.
- **Log why, then refuse.** An `Effect.logInfo` just before a declared error is kept on the span as the reason. Eval 9
  checks every declared refusal has one.

### Generated or scaffolded

`ortho generate` writes two kinds of file, and their first line says which:

```ts file=packages/generators/src/modules/render/internal/names.ts lines=3-4
export const GENERATED = "// Generated from the blueprint. Do not edit.";
export const scaffolded = (from: string) => `// Scaffolded from ${from}. Yours from now on.`;
```

| | Generated | Scaffolded |
|---|---|---|
| Where | `generated/`: the model, the frames, the endpoints, the server, SDK, CLI, MCP and docs | `src/<thing>/<verb>.ts`, one per operation with a handler |
| First line | `// Generated from …. Do not edit.` | `// Scaffolded from <declaration>. Yours from now on.` |
| Written | every time, and removed when its declaration goes | once, when the file is missing, then never again |
| Who edits it | nobody. Change the blueprint, and it follows | you, or the agent the brief names |

A scaffold is never overwritten, because the sync skips any scaffold that already exists:

```ts file=packages/generators/src/modules/sync/service.ts lines=15-19
for (const f of files) {
  const path = `${root}/${f.path}`;
  if (f.scaffold && tree.exists(path)) continue;
  tree.write(path, f.content);
}
```

So when a declaration changes, the frame changes with it, and your handler stops compiling where it no longer fits.
That is the point: the compiler tells you what to change, and nothing you wrote is lost.

### What the scaffold writes for you

**Today** the scaffold is one blank with the declaration repeated as comments:

```ts file=packages/generators/src/modules/render/internal/scaffold.ts lines=24-29
`/** ${op.description} */`,
`const ${camel(op.verb)}: Handler = (_payload, _context) =>`,
"  Effect.gen(function* () {",
said.map((s) => `    // ${s}`),
`    return yield* Handlers.blank("this handler is not written yet");`,
"  });",
```

The blank scaffold for `claim` is this, in order: the header line, the imports of `Effect` and `Handlers` and the frame's
`Handler`, the description as a doc comment, then a function that takes `_payload` and `_context` and holds only four
comments and the blank. The comments say `Payload: event, holder, seats.`, `Answer: ticket, left.`, `Steps, each its
own span: steps.load(...), steps.issue(...), steps.count(...).` and `May refuse with SoldOut.` (`scaffold.ts:9-14`).
They give no order, no move and no refusal in place. It was `src/event/claim.ts` until the handler above replaced it.

**The wired scaffold** (K5, decided; built in M1.26) writes a real function, already wired: each declared step in
declared order, the move when one is declared, and a stub for each declared refusal. Every hole is a
`Handlers.blank`, so the file compiles. For `claim` it will write:

```ts planned=M1.26 path=src/event/claim.ts
// Scaffolded from blueprint/things/event/verbs/claim.ts. Yours from now on.
import { Effect } from "effect";
import { Handlers } from "@orthograph/language-effect";
import type { Handler } from "../../generated/api/src/event/claim.handler.ts";
import { SoldOut } from "../../blueprint/things/event/errors.ts";

/** Claim a ticket for one or more seats, held under a name. */
const claim: Handler = ({ event, holder, seats }, { steps, move }) =>
  Effect.gen(function* () {
    const loaded = yield* steps.load(Handlers.blank("load: read what this step needs"));
    if (yield* Handlers.blank<boolean>("refuse SoldOut when?"))
      return yield* new SoldOut(yield* Handlers.blank("SoldOut's fields"));
    yield* steps.issue(Handlers.blank("issue: write what this step changes"));
    yield* steps.count(Handlers.blank("count: write what this step changes"));
    yield* move(yield* Handlers.blank("which outcome: onSale or soldOut?"));
    return yield* Handlers.blank("the answer");
  });

export default claim;
```

Compare it with the filled `claim` above: each blank became one line of real work, and nothing else moved. The order
of the steps is the order eval 6 checks, so a scaffold left in place can't fail eval 6 by order. An optional step
is scaffolded like any other, with a comment that it may be skipped (see `operations`).

### Blanks

A blank is a part that isn't written yet. There are two kinds, and both compile.

**A blank in a declaration** is `Blueprint.todo("…")`, which fits anywhere a declaration needs a value:

```ts file=packages/orthograph/src/modules/blanks/types.ts lines=7-11
export interface BlanksApi {
  /** `Blueprint.todo("who may call")` fits wherever a declaration needs something, until it is filled. */
  readonly todo: <T = never>(what: string) => T;
  readonly isBlank: (x: unknown) => x is Blank;
}
```

`ortho check` finds each one and names it with its file and line, as `mission has 1 blank`. The compiler leaves an
operation with a blank part out of the model, so it gets no frame and no scaffold until it is filled
(`packages/cli/src/modules/generate/generate.test.ts:20`). A blank can't stand in for a role: `allowed` must name
roles a `roles.ts` exports (F5). Tickets has no blank left, so this example is work's `mission`.

**A blank in a handler** is `Handlers.blank("…")`, what every fresh scaffold holds. It type-checks as anything, and
reaching it at run time is a defect that names what is missing:

```ts file=packages/language-effect/src/modules/handler/service.ts lines=113-116
export const Handlers: HandlerApi = {
  serve: serve as unknown as HandlerApi["serve"],
  blank: (what) => Effect.die(new BlankReached({ what })),
};
```

### `ortho prove --empty`

A project with every handler blank still compiles, serves, and runs its journeys. Each step that needs behaviour goes
red with `BlankReached`, and a step that passes anyway is labelled "proved by the description". That run is
`ortho prove --empty` (M1.16). It is how a journey is shown to fail before the builder starts (see `journeys`).

Tickets' journeys were written first, by someone other than the builder, and its handlers began as the blank scaffold
above, so every step that needed behaviour had nothing to run. Only then were the handlers written. With the
wired scaffold, `--empty` shows one red step per blank, so the run says which blank each journey needs filled.

### Unused steps

A declared step the handler never calls compiles: the frame's type can't tell. Two things catch it instead
(K5, decided; built in M1.26):

- **`ortho check` warns** when a required step's runner never appears in the handler's source. Deleting
  `steps.count(…)` from `claim` gives that warning.
- **Eval 6 is the proof.** At `ortho prove`, a successful call whose declared step ran no span fails, and so does a
  step run before one declared earlier (`packages/prove/src/modules/evals/internal/calls.ts:114`; quoted on
  `operations`). An optional step may be absent; its order is still checked.

### Who fills a blank

Whoever the brief names. `ortho brief <thing>.<verb>` prints everything needed to write one handler: the files to
read, the one file to write, the files never to touch, and the checks that must pass:

```ts file=packages/cli/src/modules/brief/service.ts lines=3-5
const forbidden = [
  "blueprint/**", "blueprint/journeys/**", "blueprint/starting-worlds/**", "journeys/**", "generated/**", "test/**",
] as const;
```

A person can follow it, and so can an agent; the factory hands it out as a task (see `factory`). The builder writes
`src/<thing>/<verb>.ts` and nothing else. The journeys were written first, by someone else, and the builder never
edits them.

## Choices

### Write it now, or leave it blank

Leave a handler blank while its journeys are being written: `ortho prove --empty` shows which steps need it. Write it
once its journeys fail for the right reasons. A blank left in a declaration is fine while a dependency is missing, as
work's `mission.tasks` waits on one, but it keeps the operation out of the model until it is filled.

### A declared error or a defect

| | Declared error | Defect |
|---|---|---|
| When | the caller asked for something the data says no to | something that can't happen did |
| How | `return yield* new SoldOut({ … })` | `Effect.die(…)` |
| The caller gets | the refusal, its code and exit code | a failure no client can match |

If a caller could fix it by asking differently, declare it. If only a code change could fix it, let it die.

### Skip a step, or mark it optional

If a successful path truly has nothing to do in a step, mark the step optional in the declaration and let the
handler skip it. Don't run a step for nothing to satisfy eval 6: it writes for nothing, and an operation's own event
would be committed for a call that changed nothing (see `operations`).

## What it is not

- **Not the operation.** The operation declares the call; the handler only does the work. See `operations`.
- **Not where roles or state are checked.** The runtime does both before the handler runs. See `roles` and
  `machines`.
- **Not a door.** Every door reaches the handler through the same wrapper; none calls it directly. See `doors`.
- **Not where data is committed.** The handler's writes go into one commit after it answers. See `stores`.
- **Not where spans are made.** Steps make spans; the handler only runs its work through them. See `traces`.
- **Not a journey.** A journey proves the handler from outside, through real operations. See `journeys`.

</Note>

<Note kind="question" id="raw-sql-in-a-handler" slice="M1.17">
  The frame offers `SqlClient` beside `Records`: the generated `Handler` type allows `Records | SqlClient.SqlClient | Auth`
  (`packages/generators/src/modules/render/internal/api.ts:97`), tickets' `claim` included. A handler that writes
  through `SqlClient` writes outside the commit, so its write isn't all-or-nothing with the move and its event, and
  won't work for a thing in another kind of store. Should the frame offer `Records` only, with raw SQL as a declared
  step kind? Ledger: HAN-01, high.
</Note>

<Note kind="question" id="frame-file-name">
  The frame's own comment says a project writes its handler in `<verb>.handler.ts`
  (`packages/language-effect/src/modules/handler/types.ts:29`). That is the generated frame's name; the project
  writes `src/<thing>/<verb>.ts`. The design docs' handler example uses an `instance` in the context and
  `steps.record` with a patch (`design/docs/index.html:435`); the real handler reads through `Records` and passes
  each step its work. Both should match the code. Ledger: HAN-05.
</Note>

<Note kind="question" id="defect-is-a-bare-500">
  A defect, `BlankReached` included, reaches a client as a bare 500 with an empty body and a decode error. Should
  there be one catch-all declared shape, so a client always gets a typed failure? Ledger: HAN-02.
</Note>
