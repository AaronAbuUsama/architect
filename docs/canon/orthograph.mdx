## The idea

Orthograph is a framework where you describe a system once and everything else is made from that description. You
write the description as TypeScript declarations in a [`blueprint`](blueprint.mdx) folder, and `ortho check` compiles
it to a model. **Each operation is enforced in exactly one place**: the wrapper on the Worker for an operation written
in Effect, or the contract for one that runs on a chain. Everything else falls out of the model and reaches that one
place: the SDK, the CLI, MCP tools and actions for the apps people build, and the [portal](portal.mdx) for the builder
who needs to understand the running system. Each of those is a **projection**: one view of the same model, made by
code, never written by hand. The one thing a description can't say is what an operation actually does. So the rule
is: **behaviour is the only freehand**. Each operation's body is a [handler](handlers.mdx) you write; everything
around it is generated, and stays generated. **The loop** is how the pieces meet: you describe, the model compiles,
journeys prove it, environments ship it, and what is missing or red comes back as new work.

## The smallest example

The example is **tickets**: free tickets for events, and nothing else. No money, no accounts. An `event` has a fixed
number of places; a `ticket` is claimed for some of them, then checked in at the door or cancelled. This is the whole
project, so you can see where each thing sits:

The loop runs through four of those folders. You **declare** in `blueprint/`, Orthograph **generates** into
`generated/`, you **write the handler** in the `src` folder, and the **journeys** prove the whole. Take one operation, claiming a
ticket, and follow it round.

**Declare.** This is the whole file `event.claim` lives in. It says what claiming is, and nothing about how it is done.
It imports the thing, the machine and the error it means, and the ticket thing it writes:

```ts file=examples/tickets/blueprint/things/event/verbs/claim.ts lines=1-18
import { Blueprint } from "orthograph";
import { Event } from "../thing.ts";
import { machine } from "../machine.ts";
import { SoldOut } from "../errors.ts";
import { Ticket } from "../../ticket/thing.ts";
import { Count } from "../../../values/counts.ts";

export default Blueprint.operation(Event, {
  description: "Claim a ticket for one or more seats, held under a name.",
  payload: { event: Event.fields.id, holder: Ticket.fields.holder, seats: Count },
  answer: { ticket: Ticket.fields.id, left: Count },
  move: machine.moves.claim,
  errors: [SoldOut],
  allowed: [Blueprint.anyone],
  steps: { load: Blueprint.step.database(), issue: Blueprint.step.database(), count: Blueprint.step.database() },
  idempotent: "request", // sent twice with one request, it issues one ticket
  budget: { p95: "150 millis" },
});
```

**Generate.** From those eighteen lines Orthograph makes every way in. Each file opens with a line saying it was
generated and must not be edited. This is the whole HTTP endpoint: its route, payload, answer and refusals come from the
declaration:

```ts file=examples/tickets/generated/api/src/event/claim.ts lines=1-12
// Generated from blueprint/things/event/verbs/claim.ts. Do not edit.
import { HttpApiEndpoint } from "effect/http-api";
import declaration from "../../../../blueprint/things/event/verbs/claim.ts";
import { SoldOut, EventNotOnSale } from "../errors.ts";

export { declaration };
export const endpoint = HttpApiEndpoint.post("claim", "/event/claim", {
  payload: declaration.payloadSchema,
  success: declaration.answerSchema,
  error: [SoldOut, EventNotOnSale],
});
export const steps = ["event.claim.load", "event.claim.issue", "event.claim.count"] as const;
```

One of those refusals was never written: `EventNotOnSale` comes from the event's machine. The rest of what `claim`
becomes:

| Projection | What it makes for `claim` | Where |
|---|---|---|
| server | the served operation: the one wrapper that enforces `event.claim` | `examples/tickets/generated/server/main.ts:32` |
| SDK | `claim(payload)` | `examples/tickets/generated/sdk/src/event/claim.ts:8` |
| CLI | the command `event claim --event … --holder … --seats …`, built on the SDK | `examples/tickets/generated/cli/src/event/claim.ts:9` |
| MCP | the tool `event.claim`, described by the declaration | `examples/tickets/generated/mcp/src/index.ts:13` |
| docs | its page: who may call, budget, payload, refusals with their codes | `examples/tickets/generated/docs/event/claim.md:37` |
| handler type | what the handler is given and may return | `examples/tickets/generated/api/src/event/claim.handler.ts:7` |
| action | a `defineAction` in agent-native's field names, built on the SDK | planned, M1.22 ([doors](doors.mdx)) |

Every one of them reaches the same served operation; none of them checks anything on its own. What each door is, and
why it holds no authority, is [doors](doors.mdx).

**Write the handler.** This is the only part of `claim` someone wrote. Orthograph scaffolded it once, from the
declaration; from then on it is yours. It imports the generated `Handler` type, so the declaration decides what it is
given and what it may return:

```ts file=examples/tickets/src/event/claim.ts lines=1-31
// Scaffolded from blueprint/things/event/verbs/claim.ts. Yours from now on.
import { Effect } from "effect";
import { Ids, Records } from "@orthograph/language-effect";
import type { Handler } from "../../generated/api/src/event/claim.handler.ts";
import { Event } from "../../blueprint/things/event/thing.ts";
import { SoldOut } from "../../blueprint/things/event/errors.ts";
import { Ticket } from "../../blueprint/things/ticket/thing.ts";

/** Claim a ticket for one or more seats, held under a name. */
const claim: Handler = ({ event, holder, seats }, { steps, move }) =>
  Effect.gen(function* () {
    const records = yield* Records;
    // The machine's check already found the event on sale, so it exists.
    const found = yield* steps.load(records.find(Event, event));
    if (!found) return yield* Effect.die(new Error(`event ${event} was checked and then not found`));
    const places = found["places"] as bigint;
    const claimed = found["claimed"] as bigint;
    const left = places - claimed;
    if (seats > left) {
      yield* Effect.logInfo("more seats asked for than places left").pipe(Effect.annotateLogs({ seats: String(seats), left: String(left) }));
      return yield* new SoldOut({ left });
    }
    // The ticket is written in the same commit as the claim, already issued.
    const ticket = yield* Ids.of(Ticket.fields.id);
    yield* steps.issue(records.insert(Ticket, { id: ticket, event, holder, seats }, "issued"));
    yield* steps.count(records.update(Event, event, { claimed: claimed + seats }));
    yield* move(seats === left ? "soldOut" : "onSale");
    return { ticket, left: left - seats };
  });

export default claim;
```

The handler counts the places left, refuses with `SoldOut` when there are too few, writes the ticket and the new count,
and picks the next state. It never checks who is calling or whether the event is on sale, never parses a request and
never names a route. The declaration already said all of that.

**Prove.** A different agent wrote the journeys before the handler existed, so they failed on a blank one. This step
of `sell-out-an-event` asks for two seats when one is left, and expects the refusal, no event and no work past the load:

```ts file=examples/tickets/journeys/sell-out-an-event.ts lines=22-29
s.step(
  "two more seats are refused: only one place is left",
  s.guest.run(claim, { event: s.world.event, holder: "Bilal", seats: 2n }, { request: "claim-2-seats" }),
  refuses(SoldOut, { left: 1n }),
  noEvents(),
  machine.isIn(s.world.event, "onSale"),
  spans({ present: ["event.claim.load"], absent: ["event.claim.issue", "event.claim.count"] }),
),
```

The step is the declaration's promise, checked against the running operation: the refusal, the state and the spans
(the evidence it leaves) all agree. `ortho prove` runs every journey and reports whether the loop closed.

Read it top to bottom; each band has its own page in this layer:

1. **The blueprint** is what you write ([blueprint](blueprint.mdx)). Plugins are mounted into it: features, adapters
   and projections ([plugins](plugins.mdx)).
2. **The model** is what `ortho check` compiles it to: one JSON, every declaration hashed. Every projection is made
   from it, never from the blueprint directly.
3. **Languages** turn the model into frames, blanks and the enforcer for each place an operation can run. **Hosts**
   are where that runs ([languages-and-hosts](languages-and-hosts.mdx)). The right-hand column, the chain, is
   illustrative until K7 settles how an operation maps to a contract.
4. **Data** lives in stores the framework owns, in sources it reaches through adapters, and in views kept from events
   ([data](data.mdx)).
5. **The doors** all go through the generated SDK or straight to the served operation, so the one enforcer decides
   every time ([doors](doors.mdx)).
6. **Evidence** comes back under the model's names, and proof and the portal read the same structure the declaration
   drew.

The loop runs through those bands in the order a change moves:

1. **You describe.** You and your agent write declarations under `blueprint/`. Built. Plugins mounted into the
   blueprint come in M1.06.
2. **It compiles.** `ortho check` compiles the blueprint to the model and checks types, rules and drift. Built.
   Blanks and journeys join the model in M1.03.
3. **Projections make the outputs.** The generators render `generated/` from the model. Built. If a generated file
   differs from what the model renders, `ortho check` fails, so nobody can edit one and keep it.
4. **Handlers fill in behaviour.** `ortho generate` scaffolds a handler for each operation, once, and never
   overwrites it ([handlers](handlers.mdx)). Built; the wired scaffold is M1.26.
5. **Journeys prove it.** A different agent writes [journeys](journeys.mdx) through the real operations. `ortho prove`
   runs them in a world, the nine evals judge the evidence, and a verdict is recorded ([proof](proof.mdx)). Built.
6. **Environments ship it.** `ortho promote` moves one exact build from environment to environment
   ([environments](environments.mdx)). Built locally; the cloud is M7.
7. **The loop closes.** The [factory](factory.mdx) turns blanks, red verdicts and drift into tasks, and only a fact
   closes one (M3.09). Until then, you close the loop yourself: you read what `ortho check` and `ortho prove` say, and
   act on it.

## Choices

**Declaration or handler?** Put it in the declaration whenever the declaration can say it. Each thing a declaration
says is generated into every door, enforced in one place, checked and traced. Each thing a handler does is only in
that handler.

| You want to say | Say it in | Because |
|---|---|---|
| who may call | the operation's `allowed` | the enforcer refuses before the handler runs, whichever door the call came through |
| a state it must be in | the machine's move | the refusal is generated |
| a way it can fail | the operation's `errors` | it gets a code, an exit code, a typed error in the SDK and a docs row |
| how it decides and what it writes | the handler | only behaviour is freehand |

**Generated client or your own?** Use the generated SDK, CLI, MCP tools and actions. Each is remade when the blueprint
changes, and each reaches the same enforcer. A hand-written client drifts the day an operation changes.

## What it is not

- **Not a one-off code generator.** Generated files are never yours. They are remade from the model, and editing one
  fails `ortho check`. Only scaffolds become yours ([handlers](handlers.mdx)).
- **Not low-code.** A handler is ordinary Effect code. Orthograph takes away the code around behaviour, not behaviour.
- **Not the blueprint.** Orthograph is the framework and its command. The [blueprint](blueprint.mdx) is what you write
  with it.
- **Not a host.** Orthograph makes what runs; a host such as Cloudflare runs it
  ([languages-and-hosts](languages-and-hosts.mdx)).
- **Not an agent-native app.** Orthograph ports what it needs from agent-native into its own Effect code and keeps
  agent-native's action field names, so its templates read naturally. Nothing of agent-native runs, and there is no
  dependency on it (K5, "Porting from agent-native"). The details are on [doors](doors.mdx) and [portal](portal.mdx).
- **Not a list of data places.** Where data lives, and who may write it, is [data](data.mdx).
