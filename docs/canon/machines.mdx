## The idea

A machine is a thing's states and the moves between them. A move names the states it may start from, the states it
may end in, and the event it emits. An operation makes at most one move, and says which. One rule decides it: **a
thing's state changes only through a declared move, and every move writes its event in the same commit as the new
state.** A call from a state the move can't start from is refused before your handler runs, with a refusal the
machine makes for you.

## The smallest example

The tickets example has two things with a machine each, an `event` and a `ticket`. Here is where they sit:

```text tree=examples/tickets/blueprint
things/
  event/  an event with a fixed number of places
    thing.ts
    events.ts  what its moves emit
    errors.ts  SoldOut, a refusal that depends on data
    machine.ts  its states and moves
    verbs/
      open.ts
      claim.ts  the operation that makes the `claim` move
      close.ts
      get.ts
  ticket/  a ticket for some seats, held under a name
    thing.ts
    events.ts
    machine.ts
    verbs/
      check-in.ts
      cancel.ts
      get.ts
```

The event's machine is the whole file. It has three states and three moves:

```ts file=examples/tickets/blueprint/things/event/machine.ts lines=1-13
import { Blueprint } from "orthograph";
import { Event } from "./thing.ts";
import * as Events from "./events.ts";

export const machine = Blueprint.machine(Event, {
  states: ["onSale", "soldOut", "over"],
  moves: {
    open: { from: [], to: "onSale", emits: Events.EventOpened },
    claim: { from: ["onSale"], to: ["onSale", "soldOut"], emits: Events.TicketsClaimed }, // the last places sell it out
    close: { from: ["onSale", "soldOut"], to: "over", emits: Events.EventOver },
  },
  notFrom: { exit: 70 }, // generates EventNotOnSale
});
```

The machine imports the thing it is for, and the events its moves emit. `claim` has two outcomes: the event stays
`onSale`, or the last places sell it out. Each move emits an event, declared beside the machine in `events.ts`. An
event is named by its export, and its fields come from the thing's:

```ts file=examples/tickets/blueprint/things/event/events.ts lines=1-7
import { Blueprint } from "orthograph";
import { Event } from "./thing.ts";
import { Count } from "../../values/counts.ts";

export const EventOpened = Blueprint.event({ event: Event.fields.id, places: Count });
export const TicketsClaimed = Blueprint.event({ event: Event.fields.id, seats: Count, left: Count });
export const EventOver = Blueprint.event({ event: Event.fields.id });
```

The compiled model draws the machine, and the refusal it made: `EventNotOnSale`, code `EV-900`, exit 70.

An operation says which move it makes. `event.claim` makes `claim`. Its whole declaration is on
[operations](operations.mdx); this is the line that names the move, and the machine it imports on line 3:

```ts file=examples/tickets/blueprint/things/event/verbs/claim.ts lines=12-12

```

The ticket has a machine too, and it has no move that creates it:

```ts file=examples/tickets/blueprint/things/ticket/machine.ts lines=1-13
import { Blueprint } from "orthograph";
import { Ticket } from "./thing.ts";
import * as Events from "./events.ts";

// A ticket starts issued: `event.claim` writes it in that state, in the same commit as the claim.
export const machine = Blueprint.machine(Ticket, {
  states: ["issued", "checkedIn", "cancelled"],
  moves: {
    checkIn: { from: ["issued"], to: "checkedIn", emits: Events.TicketCheckedIn },
    cancel: { from: ["issued"], to: "cancelled", emits: Events.TicketCancelled },
  },
  notFrom: { exit: 72 }, // generates TicketNotIssued
});
```

Nothing in it starts from `[]`. Another operation creates the ticket, in a state of its own choosing (see "A thing
another operation creates", below).

## How it works

A move happens in three places in one call: a check before the handler, a choice inside it, and the state and event
in the commit after it.

### Before the handler: the wrong-state check

Once the caller has passed the role check, the machine checks the state
(`packages/language-effect/src/modules/handler/service.ts:57`):

```ts file=packages/language-effect/src/modules/handler/internal/move.ts lines=30-40
export const checkFrom = (op: Operation, refusal: string | undefined, payload: object, unit: Unit) =>
  Effect.gen(function* () {
    const move = op.move;
    if (!move || move.from.length === 0 || refusal === undefined) return;
    const subject = subjectOf(op, payload);
    if (subject === undefined) return;
    const found = yield* unit.read(op.thing, subject);
    if (!found) return;
    const state = found.state ?? "none";
    if (!move.from.includes(state)) return yield* Effect.fail(new NotFrom({ _tag: refusal, state }));
  });
```

- A move with `from: []` creates the thing, so there is nothing to check. That is `open`.
- The instance is the payload's field declared as the thing's own id: `claim`'s `event: Event.fields.id`
  (`packages/language-effect/src/modules/handler/internal/move.ts:14`). If it isn't found, the machine says nothing:
  see the note `missing-instance`.
- If the state isn't one the move starts from, the call fails with the machine's refusal, carrying the state it
  found. The handler never runs, and nothing is written.

That refusal is generated, never written. The compiler names it after the thing and its first state, gives it the
number 900 so adding an error never moves it, and takes the exit you gave (`notFrom: { exit: 70 }`). Over HTTP it is a
409 (`examples/tickets/generated/api/src/errors.ts:8`). A journey names it as `machine.notFrom`, with the state it
expects. Once the last places are claimed, the event is sold out, and a further claim is refused by the machine:

<Scenario journey="examples/tickets/journeys/sell-out-an-event.ts" step="a further claim is refused: a sold out event is not on sale" />

The same refusal covers every move that starts from the wrong state. An event that is over refuses a claim, and would
refuse a second close too, though `close` may start from `soldOut` as well as `onSale`. That name is the note
`refusal-name`:

<Scenario journey="examples/tickets/journeys/an-event-that-is-over-sells-nothing.ts" step="a claim is refused: an event that is over is not on sale" />

The ticket's machine refuses in the same way, under its own name. A cancelled ticket is not issued, so checking it in
is refused as `TicketNotIssued`, code `TI-900`, exit 72:

<Scenario journey="examples/tickets/journeys/cancel-a-ticket.ts" step="checking in a cancelled ticket is refused" />

Reading the instance here also fixes the version the commit is guarded by. So if a close lands between this check and
a claim's commit, the claim's commit is a conflict and runs again, and then the check refuses it. How the version
guard works is on [stores](stores.mdx).

### Inside the handler: choosing the outcome

The handler gets `move` and calls it once, with the state it ends in. A move with one `to` may be called with
nothing, or its one state, as `close` does (`examples/tickets/src/event/close.ts:8`). A move with several must be
told which. This is the end of the event's claim, the whole handler being on [handlers](handlers.mdx):

```ts file=examples/tickets/src/event/claim.ts lines=26-28
yield* steps.count(records.update(Event, event, { claimed: claimed + seats }));
yield* move(seats === left ? "soldOut" : "onSale");
return { ticket, left: left - seats };
```

An outcome the move doesn't declare dies as the handler's bug. The span says what was asked first, as `move.to`, so
the wrong outcome is evidence too (`packages/language-effect/src/modules/handler/internal/move.ts:48`). A handler that
refuses never calls `move`, so nothing moves. When two seats are asked for and only one place is left, the handler
refuses with `SoldOut`, a refusal of its own, and the event stays on sale:

<Scenario journey="examples/tickets/journeys/sell-out-an-event.ts" step="two more seats are refused: only one place is left" />

### A thing another operation creates

The event's `open` has `from: []`, so it creates the event. A ticket has no such move: it comes into being inside
`event.claim`, which is an operation of another thing, with the event's move. The handler inserts the ticket and names
the state it starts in:

```ts file=examples/tickets/src/event/claim.ts lines=23-25
// The ticket is written in the same commit as the claim, already issued.
const ticket = yield* Ids.of(Ticket.fields.id);
yield* steps.issue(records.insert(Ticket, { id: ticket, event, holder, seats }, "issued"));
```

So the one commit holds the ticket in `issued`, the event's new count and state, and the claim's event. The ticket's own
machine takes over from there: `checkIn` and `cancel` both start from `issued`, and nothing leaves `checkedIn` or
`cancelled`. A claim emits the event's `TicketsClaimed`; the ticket's events are for its own two moves. A move belongs
to the operation of its own thing, so a cancelled ticket does not put its seats back: that would be a move of the
event, made from the ticket's operation.

What a handler gets and returns is [handlers](handlers.mdx).

### After the answer: the state and the event, in one commit

Once the handler has answered and its answer is checked, the move is applied
(`packages/language-effect/src/modules/handler/internal/move.ts:56`). The event's fields are taken from the instance
as this call left it, then the payload, then the answer. A field found in none of them dies. `TicketsClaimed`'s `left`
is in the answer, and its `event` and `seats` are in the payload. Then:

```ts file=packages/language-effect/src/modules/handler/internal/move.ts lines=69-74
// The journal is a record anyone who reads it can see: a secret or private field of the event is not written to it.
const fields = Object.fromEntries(Object.entries(encoded).filter(([k]) => journalled(move.emits.fields, k)));
yield* unit.setState(op.thing, subject, outcome);
const trace = yield* Effect.currentSpan.pipe(Effect.map((s) => s.traceId), Effect.orElseSucceed(() => ""));
yield* Effect.annotateCurrentSpan({ "event.name": event });
return { trace, operation: name, move: move.key, subject, event, fields } satisfies Entry;
```

The new state goes into this call's writes, and the event becomes a journal entry. Both go into the one commit with
the handler's own writes (`packages/language-effect/src/modules/handler/service.ts:71`). So the state and its event
land together or not at all. A handler that dies after writing leaves nothing behind
(`packages/language-effect/src/modules/handler/handler.test.ts:267`). The commit itself is [stores](stores.mdx).

The state is kept beside the thing's fields, not as one of them. In D1 it is a `state` column, empty until the first
move sets it (`packages/generators/src/modules/render/internal/worker-config.ts:64`).

### What an event is for

An event is the record of a move: what happened, to which instance, in which call. Today it is used in three ways:

- **The journal.** Every entry names the call's trace, the operation, the move, the instance and the event's public
  fields (`packages/language-effect/src/modules/journal/types.ts:4`). It is the system's own history, written with the
  state it explains.
- **Proof.** `ortho prove` finds a step's events by its trace. That is how a journey checks a move happened, with
  `emits(TicketsClaimed, …)`, or that nothing moved, with `noEvents()`.
- **The trace.** The operation's span carries `move.name`, `move.to` and `event.name`. See [traces](traces.mdx).

Here a journey checks both the event and the state the move left, when the last place is claimed:

<Scenario journey="examples/tickets/journeys/sell-out-an-event.ts" step="the last place is claimed and the event is sold out" />

Two more are designed. The outbox delivers every move's event at least once, to whatever listens (M5.04). And a view
is a list kept from events, so it can list things across stores and entities (M5.05, on [views](views.mdx)).

### Events without a move

Today an event comes only from a move: no machine, no event. That leaves an operation that writes but has no state to
change, such as editing a draft's text, with nothing in the journal. K5 settles it (Q5): an operation may declare
`emits:` of its own, and its event is committed with the call's writes, only when the call succeeds and only when it
wrote something. That is built in M3.16, and it is declared on the operation, so it is on
[operations](operations.mdx), not here:

```ts planned=M3.16 path=blueprint/things/draft/verbs/edit.ts
export default Blueprint.operation(Draft, {
  description: "Change a draft's text.",
  payload: { draft: Draft.fields.id, text: Body },
  answer: {},
  emits: Events.DraftEdited,
  steps: { record: Blueprint.step.database() },
});
```

### Why a machine, and not a status field

A status field is a value any handler can set to anything. A machine makes four things true that a field can't:

- **Only declared moves.** `close` can't start from `over`, and `claim` can't end in `over`. The runtime checks
  `from` before the handler and `to` after it, so a handler can't move the thing anywhere the machine doesn't allow.
- **One refusal, made for you.** A call from the wrong state is refused the same way at every door: the same name,
  the same code, the same exit, and a journey can name it. With a status field, each handler writes its own check, or
  forgets to.
- **Every change leaves an event.** A move writes its event in the same commit as the state. Setting a field leaves
  nothing to prove from, and nothing a view can be kept from.
- **The model can draw it.** States and moves are in the model, so the docs and the portal show the machine as a
  diagram, not a column.

## Choices

### One outcome, or several

Give `to` one state when the move always ends there: `close` always ends `over`. Give a list when the handler decides
from the data: `claim` ends `onSale` or `soldOut`, depending on how many places are left. The handler must then say
which, and a wrong one dies.

### Where a move may start

`from: []` makes a move that creates the thing, like the event's `open`. Otherwise list every state it may start from.
A state you leave out is refused by the machine, before any of your code runs. A thing that another operation
creates, like the ticket, has no `from: []` move at all, and its first state is the one that operation writes.

### Which fields an event carries

Put in an event what a reader of the journal needs to know what happened: the instance's id, and the facts of the
move. `TicketsClaimed` carries the event, the seats claimed and how many places are left. Only public fields are
written, so a secret or private field in an event is dropped from the journal (see [things](things.mdx)). Fields a
call doesn't have die, so each one must come from the instance, the payload or the answer.

### A machine, or none

A thing whose life has stages gets a machine: an event, a ticket, an invitation. A thing that is only kept and
changed, like a person, needs none. Its operations declare no `move` and, until M3.16, emit no events.

## What it is not

- **Not a field.** The state is not one of the thing's fields, and a handler doesn't write it. See [things](things.mdx).
- **Not a data refusal.** `SoldOut` depends on how many seats are asked for, so it is declared in `errors.ts` and
  raised by the handler. The machine's refusal depends only on the state. Refusals in general are
  [operations](operations.mdx).
- **Not a role check.** `NotAllowed` says who may call, and it comes first. Everyone may call the event's and the
  ticket's operations (`Blueprint.anyone`), so tickets never shows it: see [roles](roles.mdx).
- **Not a workflow.** A machine doesn't wait or run on its own. Every move is one call. Work that waits is
  [workflows](workflows.mdx).
- **Not a view.** An event is one move's record. A list built from many events is a view: see [views](views.mdx).

## Notes

<Note kind="decision" decision="D2">
  A handler makes its move with `move(to?)`, and the wrapper applies it after the answer (#25). The outcome is written
  on the span before it is checked, so an undeclared one dies and is still evidence.
</Note>

<Note kind="decision" decision="D3">
  Refusal codes are stable across languages, and the machine's own refusal is always 900 (`SH-900`), so adding an
  error never moves it.
</Note>

<Note kind="decision" decision="K5">
  Q5: `emits:` on an operation with no machine, committed with the call's writes, only on success and only when the
  call wrote. Built in M3.16, owned by [operations](operations.mdx).
</Note>

<Note kind="status" slice="M5.04">
  Today an event reaches the journal and nothing else. Nothing listens to it yet.
</Note>

<Note kind="status">
  D2 #25 says an event's fields come from the answer, then the payload. The code also reads the instance as the call
  left it (`packages/language-effect/src/modules/handler/internal/move.ts:62`), so an event can carry a fact of the
  instance that is in neither the payload nor the answer. This page follows the code.
</Note>

<Note kind="question" id="refusal-name">
  Ledger `MAC-02`. The machine has one refusal, named after its first state
  (`packages/compiler/src/modules/model/internal/describe.ts:72`). So closing an event that is over is refused as
  `EventNotOnSale`, though `close` may also start from `soldOut`. The comment on the type says `<Thing>Not<State>`
  (`packages/orthograph/src/modules/machines/types.ts:23`), which reads as if the name followed the move. Should the name
  say what is wrong for every move, such as a refusal per move, or one neutral name? Renaming it is a major change
  once released, since clients match on the name.
</Note>

<Note kind="question" id="move-not-made">
  An operation that declares a move, and whose handler answers without calling `move`, commits with no new state and
  no event. Nothing refuses it. For a move with one outcome, should the runtime make the move when the handler
  answers? Or should a handler that answers without moving die, as an undeclared outcome does? No ledger row owns it
  yet.
</Note>

<Note kind="question" id="missing-instance">
  A move on an instance that doesn't exist is refused by nobody. `checkFrom` returns when the instance isn't found
  (`packages/language-effect/src/modules/handler/internal/move.ts:30`), and in acme the role check has already refused
  the call. But the event's operations are open to anyone, so a claim on an event id that was never opened reaches the
  handler, which dies (`examples/tickets/src/event/claim.ts:15`): a defect, not a refusal a caller can name. Should the
  machine refuse a missing instance, with a generated `NotFound` beside `EventNotOnSale`? Ledger: MAC-07, no slice owns it yet.
</Note>
